# 設計メモ: 仕分けを「緩い被覆」へ作り替える（クラスタリング再設計）

**状態: 提案。実装前。** `docs/design-preprocess-merge.md` の §4.3〜§4.9.2 を
置き換えることを意図している。前提となる実験結果は PR #11（フェーズ 2・視覚
クラスタリング）と PR #12（フェーズ 2.6・重なりによるグループ分け／**棄却済み**）
にある。

この文書は 3 つのことをする。

1. **目的関数を置き換える**（§1）— 「部屋を正しく見分ける」から
   「Object Capture が処理できる塊で全体を覆う」へ。
2. **Gemini が提示したクラスタリング手順を検証する**（§2）— 3 段のうち
   1 段は条件付きで採り、1 段は保留、1 段は**この問題には向かない**。
3. **代わりの設計を出す**（§3 以降）— 撮影順のバックボーン + 重なりつきの被覆。
   実装計画と、実写真での go/no-go の測り方まで。

---

## 1. 目的関数を置き換える

これまでの `sort` は暗黙にこう定義されていた。

> 写真を**部屋ごとに正しく分割**し、隣接するグループには共有写真を数枚入れる。

この定義のもとで 2 つのフェーズが実データで失敗した。失敗の仕方が両方とも同じで、
**「同じ場所か」を判定しようとして、判定できずに壊れた**。

| | 何を測ろうとしたか | 実写真 1424 枚での結果 |
| --- | --- | --- |
| #11 フェーズ 2 | feature print の距離で「同じ場所」 | 97% が 1 か所に潰れ、証拠として使えず（`roomsNotDiscriminating`） |
| #12 フェーズ 2.6 ① | 位置合わせ後の画素相関 | 骨格の的中率 45%・平均次数 3.56 → 細い鎖状のグループ |
| #12 フェーズ 2.6 ② | ブロックごとの局所一致率 | 骨格の的中率 **1.1%**・93% の写真が孤立 → 仕分け不能 |

利用者からの新しい前提は、この定義そのものが過剰だったことを示している。

- Object Capture は **2〜3 部屋ぶんを一度に処理できる**。部屋単位に切り分ける
  必要は無い。
- **異なる部位の写真が紛れても、計算に使えない写真は API 側が除外する。** 混入の
  コストは「その写真ぶんの時間」でしかない。
- 分割したモデル間の**重複は多いほうが良い**。合成（§5）の対応点がそれだけ増える。

したがって新しい定義はこうなる。

> **Object Capture が一度に処理できる大きさの塊で、写真全体を覆う。**
> 隣り合う塊は**大きく重ねる**。塊の中身が 1 部屋か 3 部屋かは問わない。

### 1.1 この設計を貫く 1 行

**混入のコストは分断のコストよりはるかに小さい。**

古い設計は暗黙に逆を仮定していた（「無関係な写真を持ち込むぶん有害」— §4.4）。
向きが逆になったので、判断に迷ったときの倒し方が全部変わる。

| 迷ったとき | 旧 | 新 |
| --- | --- | --- |
| この写真を入れるか | 証拠が無ければ入れない | **入れる**（API が捨てる） |
| ここで切るか | 上限を超えたら切る | **切らない側に倒す**（上限まで粘る） |
| 共有写真を何枚 | 15 枚（固定） | **塊の 30% 前後**（数十枚） |
| 判定できなかった組 | 保留（落とさない） | **そもそも判定しない** |

「判定できないなら判定しない」が要点で、#11 / #12 で費やしたコストの大半は
**答えが出ない問いに答えようとしたぶん**だった。

## 2. 提示された手順の検証

> Step 1 Feature Print で候補ペア（上位 30〜50）→ Step 2 SIFT/ORB + RANSAC で
> 幾何検証 → Step 3 Louvain / Normalized Cut でコミュニティ抽出

**総論: Step 1・2 は写真測量の定石として正しく、#12 の失敗の診断も正確。**
実際 COLMAP 等の SfM は「検索で候補を絞る → 特徴点の対応を幾何検証する」という
まったく同じ構造をしている。#12 が失敗した理由（3 次元の場面を別の立ち位置から
撮った 2 枚を 1 枚の 2 次元変換では揃えられない）と、その正しい対処が疎な特徴点の
対応であることも、そのとおり。

**ただし Step 3 はこの問題には向かず、Step 2 はこのリポジトリの制約と衝突する。**
そして最大の問題は、**§1 の新しい目的関数のもとでは Step 1〜3 の全体が要らない**
ことにある。順に見る。

### 2.1 Step 1（feature print で候補ペア）— **条件付きで採る。ただし未測定**

候補を出すだけなら閾値が要らず、**順位さえ意味を持てばよい**。#11 が失敗したのは
「距離に絶対的な閾値を置いた」ことであって、順位づけまで否定されたわけではない。
コストも軽い（2000 枚で 200 万ペア、数秒）。

**ただしこの現場で順位が意味を持つことはまだ測っていない。** #11 の実測では
「同じ壁の連続撮影で 0.2 前後・別の部屋で 0.3 前後」と帯が狭かった。帯が狭いこと
自体は順位を否定しないが、**帯の中で順序が入れ替わっていれば上位 30 件は無意味**
になる。§5.1 に、この 1 点だけを確かめる測り方を置いた。**これが通らなければ
Step 1 は成立せず、Step 2 以降も自動的に成立しない。**

### 2.2 Step 2（SIFT/ORB + RANSAC）— **正しいが、いま採るには高い**

原理は正しく、#12 の代替として唯一まっとうな方法でもある。採らない理由は 4 つ。

1. **外部依存。** OpenCV の導入は CLAUDE.md の「外部依存を増やさない」方針と
   正面から衝突する。SwiftPM に C++/ObjC++ ターゲットを足すだけでなく、
   ユニバーサルバイナリ・ad-hoc 署名・`.app` への同梱（`package-app.sh`）・
   同梱チェック（`build.yml`）がすべて増える。数十 MB のバイナリ資産も入る。
2. **Vision は特徴点の記述子と対応付けを公開していない**（§4.9.2 で確認済み）。
   依存を増やさずにやるなら**自前実装**になる。FAST/Harris + 向き付き BRIEF +
   ハミング照合 + RANSAC で、純ロジックとして書けはする（むしろこのリポジトリの
   テスト方針には合う — 画素配列の上の決定的な計算なので全部テストできる）。
   規模は 600〜1000 行程度。
3. **計算量の見積もりが甘い。** SIFT の総当たり照合は、1 枚 2000 点・128 次元で
   1 ペアあたり 5 億 flop 規模になる。1424 枚 × 上位 40 件 = 約 5.7 万ペアなら
   10¹³ flop 台で、GPU も FLANN も無しには回らない。ORB（500 点・256 bit）まで
   落として popcount で殴れば 1 ペア 10⁶ 命令規模、5.7 万ペアで 10¹¹ 命令 —
   マルチコアで数分〜十数分。**やるなら ORB 一択**で、SIFT を挙げている時点で
   規模の検討が抜けている。
4. **RANSAC が万能ではない。** 提示文は「見た目が似ているだけの別の部屋を完全に
   切り捨てられる」としているが、2 つの既知の破れ方がある。
   - **平面退化。** 基礎行列は場面が平面に近いと不定になる。**白い壁の室内は
     まさにこの領域**で、退化した解に大量のインライアが乗る。対処
     （H と F を当てて比べる / QDEGSAC）まで込みで設計しないと、#12 と同じ
     「もっともらしいが無意味な判定」を別の形で作る。
   - **反復構造。** 同じ建具・同じ壁紙が並ぶ建物では、幾何検証を通ってしまう
     偽の対応（SfM で言う doppelgänger）が実在する。「完全に」は言い過ぎ。

**結論: 疎な特徴点の幾何検証は、やるなら自前 ORB + H/F 併用。だが §1 の目的関数の
もとでは、これはグループ分けの本体には要らない**（§3.5・§3.6）。

### 2.3 Step 3（Louvain / Normalized Cut）— **この問題には向かない**

ここが最も強く反対する点で、理由は 4 つある。**仮に Step 2 が完璧なシーングラフを
作れたとしても、Step 3 は正しい答えを出さない。**

**(1) 制約が入らない。** 実際の制約は「1 塊 ≤ N 枚」というハードな容量制約だが、
モジュラリティ最大化にはそれを表現する場所が無い。LDK + 廊下が繋がった 900 枚の
コミュニティと 3 枚のコミュニティが並んで出てくるだけで、**そのあとに結局
容量制約つきの分割が必要になる**。順序が逆で、容量制約つき分割が本体、
コミュニティ抽出はその前処理でしかない。

**(2) 解像度限界と不安定性。** モジュラリティには解像度限界（Fortunato &
Barthélemy 2007）があり、大きなグラフでは小さな部屋が隣の大きなコミュニティへ
必ず吸収される。加えて Louvain は最適解の縮退が大きく、初期順序で結果が変わる
（Leiden 法が生まれた動機そのもの）。**同じ写真フォルダを 2 回仕分けて違う答えが
出るツール**は、利用者が閾値を調整する手がかりを失う。

**(3) 正規化カットは、合成にとって最悪の場所で切る。** これが決定的。

> Ncut は「エッジが最も細くなる場所（＝ドアの前）」で切る。
> **そこはまさに、切ってはいけない場所である。**

合成（§5）はグループ間の相似変換を共有写真のカメラ姿勢から解く。境界の共有写真が
少ないほど変換は不安定になり、共線退化にも近づく。**細いボトルネックで切るという
ことは、対応点が最も少ない場所で切るということ**で、目的に対して符号が逆になって
いる。§1.1 の「重複は多いほど良い」と正面から矛盾する。

もしどうしても切るなら、**切ったあとに境界の周りへ厚い襟（collar）を付け直す**
必要がある。つまり求めているのは**分割（partition）ではなく被覆（cover）**で、
これは §3.2 で正面から扱う。

**(4) 撮影順の連続性を失う。** グラフ分割の出力は撮影順の連続区間にならない。
既存の設計はここに 2 つ依存している。

- `--sample-ordering sequential` を使ってよいかどうか（`groups[].sequential`）。
  Object Capture に「並びが隣接している」と伝えられれば速く確実になる。
- 境界が 1 か所に定まるので、そこに共有写真を置けば必ず隣接が作れる（§4.3）。

**(5) 部屋を見分けること自体がもう要件ではない。** §1 のとおり 2〜3 部屋がひと塊で
構わない。「リビングのクラスタ / キッチンのクラスタ」を作るのは、いま解くべき
問題より難しい問題を解いている。

### 2.4 検証のまとめ

| | 判定 | 理由 |
| --- | --- | --- |
| Step 1 feature print で候補 | **条件付き採用** | 閾値でなく順位なら成立しうる。ただし §5.1 で実測してから |
| Step 2 疎な特徴点 + RANSAC | **保留（フェーズ 3 以降の任意機能）** | 原理は正しいが、外部依存 or 自前 1000 行。平面退化の対処込み。§1 のもとでは本体に不要 |
| Step 3 Louvain / Ncut | **不採用** | 容量制約が入らない・不安定・**合成にとって最悪の場所で切る**・撮影順を失う・そもそも部屋を見分ける要件が無い |

## 3. 提案する設計: 撮影順のバックボーン + 重なりつきの被覆

### 3.1 バックボーン = 撮影順

**手持ちで歩きながら撮った写真は、撮影順に隣り合うものが必ず重なっている。**
これは統計的な相関ではなく撮影という物理過程からの帰結で、#11 / #12 が測ろうと
していた「同じ場所か」より**因果的に強い**。実データでの失敗は、いずれもこの
バックボーンを弱い証拠で上書きしようとして起きた。

順序の決め方は次の優先順位で、**どれを使ったかを manifest に必ず書く**。

1. EXIF `DateTimeOriginal`（+ `OffsetTimeOriginal` があれば UTC 確定）
2. ファイル名の連番（`IMG_3619` 等。同一機種の連番は時刻と等価）
3. ファイル更新日時
4. **feature print の貪欲最近傍鎖** — 上の 3 つがどれも無い群（§3.4）にだけ使う。
   閾値を置かず順位だけを使うので、§2.1 の条件が満たされていれば成立する。
   外れても「その群の並びが悪くなる」だけで、他の群には波及しない。

サブフォルダは**順序より強い境界**として扱う（撮影者が既に分けている）。

### 3.2 分割ではなく被覆（cover）にする

ここが設計の中心。**塊は「切って作る」のではなく「窓をずらして作る」。**

```
撮影順  ─────────────────────────────────────────────────────────
窓 1    [========================]
窓 2                  [========================]
窓 3                                [========================]
                      ^^^^^^^^^^^^^  ← 共有区間（連続した撮影の一続き）
```

塊の大きさ `C`（`--max-per-group`）と重なり率 `r`（新設 `--overlap-ratio`）から
ストライド `s = C(1-r)` で窓を並べるだけ。1424 枚での見積もりは次のとおり。

| C | r | 窓の数 | 共有枚数/隣接 | 総処理枚数（倍率） |
| --- | --- | --- | --- | --- |
| 150 | 0.20 | 12 | 30 | 1,800（1.26×） |
| 200 | 0.30 | 10 | 60 | 2,000（1.40×） |
| **200** | **0.35** | **11** | **70** | **2,200（1.54×）** |
| 300 | 0.40 | 8 | 120 | 2,400（1.69×） |

**この形にすると、これまで解けなかった問題が問題でなくなる。**

- **共有写真が「実際に重なっている」ことを確かめる必要が消える**（§4.6.1 が丸ごと
  不要になる）。共有区間は**撮影順に連続した一続き**なので、両側のどちらとも
  重なっていることが撮影過程から保証される。#11 が Vision の位置合わせで、#12 が
  画素相関で確かめようとしていたのは、まさにこの性質だった。
- **`groups[].sequential` が常に真になる。** `--sample-ordering sequential` を
  無条件で使える。
- **`_unassigned` が原理的に空になる。** すべての写真がいずれかの窓に入る。
  「小さすぎるグループの吸収」（§4.6.2）も要らない — 末尾が短ければ前の窓へ畳む。
- **隣接が必ず作れる。** 隣接は「窓が重なっている」ことそのもの。

代償は総処理枚数が 1.4〜1.7 倍になることだが、**利用者の判断としてこれは
「プリプロセスに時間を掛けるより意味のあるデータ」**であり、いま `sort` が
費やしている解析時間（1424 枚のデコード + Vision 推論 + 16,224 組の位置合わせ）を
考えれば、差し引きで悪化しない可能性すらある。

### 3.3 境界は「良いシーム」へスナップする（切る判断ではなく、ずらす判断）

窓の境界は等間隔である必要はない。**理想位置から ±20% の範囲で、最も「切れ目
らしい」位置へずらす。** 切るかどうかは容量が決めるので、**弱い証拠は「どこで」
にしか効かせない** — これが #11 / #12 との決定的な違い。

シームらしさの材料（あるものだけ使う。既存の証拠をそのまま流用できる）:

| 材料 | 意味 | 出所 |
| --- | --- | --- |
| 撮影時刻のギャップ | 立ち止まった（撮影ガイド §12-2） | EXIF |
| 露出 EV の段差 | 屋外 → 屋内など環境が変わった | EXIF |
| サブフォルダの変化 | 撮影者が分けた | 入力構成 |
| GPS / 高度の跳ね | 階が変わった | EXIF（信用度の足切りつき） |
| feature print 距離の跳ね | 見ている場所が変わった | Vision（**順位でなく前後差**なので閾値が要らない） |

**弱い証拠がすべて欠けていても、等間隔で切れるだけで破綻しない。** ここが
「証拠が無いと何も決まらない」旧設計との違い。

### 3.4 異物を隔離する（測り方と独立に観測された事実）

#12 のコメントが実データで名指しした 2 つは、判定手法とは無関係に効く。

**(1) EXIF の無い写真がゴミ箱を作る。** SNS 経由のハッシュ名 JPEG（別日・別機種）が
group-01 / group-17 に固まり、**屋内外の混在の正体はこれだった**。撮影順に乗らない
写真をバックボーンへ混ぜてはいけない。

→ **別の群として隔離し、その群だけで §3.1-4 の順序づけと §3.2 の窓を作る。**
捨てるのではなく、独立した塊として出す（`foreign-01/` 等）。混入のコストは低いが、
**順序を壊すコストは高い**。

**(2) 画角が 35mm 換算 13〜26mm の 14 種類混在。** iPhone が寄ると超広角へ自動で
切り替わるため。Object Capture がまとめて写真をスキップする直接の原因である
可能性が高い。

→ **分割はしない**（同一シーンを別レンズで撮ることは正常で、EXIF に焦点距離が
あれば API 側で扱える）。ただし**焦点距離の欠損は隔離の対象**にする。診断
`groupMixesFocalLengths` は残し、スキップが多い窓との相関を見られるようにする。

### 3.5 ループ閉じ込みは「グループ分け」ではなく「隣接」でやる

「一度離れて戻ってきた撮影」は、旧設計では**同じグループにまとめるべきもの**
だった。新設計では**まとめる必要が無い** — 必要なのは、離れた 2 つの窓が同じ場所を
写していると `merge` に伝えること、つまり `adjacency` に 1 本足すことだけ。

失敗のコストが劇的に下がる点が重要。

| | 旧（グループ分けの本体） | 新（隣接の追加） |
| --- | --- | --- |
| 見落とすと | グループが割れる／混ざる | 合成のループ誤差が残る（報告できる） |
| 誤検出すると | 無関係な写真が同じフォルダへ | 誤った隣接 1 本（`merge` の RANSAC が落とす） |
| 必要な精度 | 高い | **低い** |

**ここが §2.2 の疎な特徴点マッチングを入れるとしたら唯一の正しい場所。**
候補は「窓ペア × 上位数組」で数百組に収まり、`OverlapSurvey`（#12 の予算配分。
判定手段と独立に設計されている）がそのまま使える。**フェーズ 3 以降の任意機能で
よく、無くても仕分けは成立する。**

### 3.6 幾何の真実は Object Capture 自身に出させる（最も筋が良い経路）

利用者の「もっと API の処理に頼ってよい」を最後まで押すと、ここに行き着く。

**`PhotogrammetrySession.Request.poses` は、写真ファイルの URL に紐づいたカメラ
姿勢を返す**（§2 で確認済み・macOS 14+）。これは Apple の SfM が実際に解いた
**本物の幾何**で、自前 ORB + RANSAC が近似しようとしているものの完成品である。

したがって:

1. `sort` は安く緩く窓を作る（§3.2）。**幾何は一切測らない。**
2. 窓ごとに再構成する。**このとき `poses` も要求する。**
3. 返ってきた姿勢が、その窓の中で**実際に何が繋がったか**を教える。
   - 姿勢が付かなかった写真 = API が使えなかった写真
   - 姿勢の分布 = 窓が空間的に一続きかどうか
   - 隣接窓の共有写真の姿勢 = **合成の対応点そのもの**（§5.2）
4. 繋がらなかった箇所だけ、重なりを増やして**その窓の周りだけ作り直す**。

**プリプロセスで解けなかった問題が、本処理の副産物として解ける。** しかも
`merge` が必要とする対応点と同じものなので、追加コストはほぼゼロ（`poses` は
メッシュ生成・テクスチャ生成を伴わないので単独なら軽い）。

`sort` → 再構成 → `poses` → 必要なら `sort` をやり直す、という**フィードバック
ループ**が本来の形で、これは §5 の `merge` 設計と自然に一体化する。

## 5. 実データでの検証手順（写真を共有せずに判断する）

§4.9.2 の教訓 —「画素の見え方に依存する判定は、合成データでは経路の確認しか
できない」— を制度として守る。**実装前に測る。**

### 5.1 go/no-go: 撮影順のバックボーンは意味を持つか

**この設計全体が乗っている唯一の仮定**を、1 つの数で確かめる。

```
A = median( featurePrint距離(i, i+1) )      // 撮影順で隣り合う組
B = median( featurePrint距離(ランダムな組) ) // 無関係な組の水準
比 = A / B
```

- **比 < 0.6** → 撮影順は場所の近さを反映している。**設計を進めてよい。**
- 比 ≈ 1.0 → 撮影順が場所と無関係（バラバラの記録用撮影）。バックボーンは
  成立しない。§3.1-4 の貪欲鎖を全体へ適用する設計へ切り替える。

**同じ計算で §2.1（Step 1 の成否）も決まる。** 「i±1 が i の feature print 上位
30 件に入る割合」= 順位版の再現率を並べて出す。**これが低ければ Step 1 は死んで
おり、Step 2 の候補生成も成立しない。**

いずれも #11 が既に計算している距離行列から出る。**写真を含まない数値 2 つ**なので
そのまま共有できる。

### 5.2 仕分けそのものの評価

`--dry-run` の manifest だけで見る。

| 見るもの | 期待 |
| --- | --- |
| 窓の数と各枚数 | 1424 枚で 10〜12・各 200 枚前後 |
| `_unassigned` | **0 枚**（構成上そうなるはず。0 でなければバグ） |
| `foreignPhotos` | SNS 経由の群がここに出ているか |
| `adjacency[].sharedCount` | 隣接ごとに 50〜70 |
| `orderingSource` | `exif` が大半 |

### 5.3 最終的な合否は実機の再構成でしか出ない

**これが唯一の本当の評価。** #12 が 2 度外したのは、ここへ到達する前に合成データの
数字で一般化したため。

| 見るもの | 合格 |
| --- | --- |
| 各窓の再構成 | error 6（位置合わせ失敗）が出ない |
| スキップされた写真の数 | 窓あたり数枚（27 枚・35 枚のような塊にならない） |
| `poses` が付いた写真の割合 | 高い。低い窓は空間的に一続きでない |
| 隣接窓の共有写真の姿勢 | **両側で得られる**（§3.6・合成の対応点になる） |

## 7. この設計が間違っているとしたら、どこか

正直に書いておく（§4.9.2 の反省をこの文書自身にも適用する）。

1. **撮影順が場所と無関係な現場では成立しない。** §5.1 で最初に測る。
2. **`maxPerGroup` の上限が推測。** 200 枚が実機で通らなければ窓が増え、
   重なりの利得が相対的に小さくなる。実機で測って決める。
3. **窓の中で API が「2〜3 部屋」を実際に処理しきれるかは利用者の 1 回の観察に
   依存している。** これが楽観的だった場合、窓を小さくして数を増やすことになる
   （設計は壊れず、パラメータの調整で済む）。
4. **ループ閉じ込み（§3.5）を後回しにしているので、一度離れて戻った撮影は
   当面ループ誤差として残る。** 報告はできるが直せない。§5 の全体最適化までは
   「どこが閉じていないか」を言うに留まる。
