## 1. 何を作るのか

### 1.1 目的関数

これまでの `sort` は暗黙にこう定義されていた。

> 写真を**部屋ごとに正しく分割**し、隣接するグループに共有写真を数枚入れる。

この定義のもとで 3 つの試みが実データで失敗した（§7）。失敗の仕方はどれも同じで、
**「同じ場所か」を判定しようとして、判定できずに壊れた**。

新しい定義はこうする。

> **Object Capture が一度に処理できる大きさの塊で、写真全体を覆う。**
> 隣り合う塊は**大きく重ねる**。塊の中身が 1 部屋か 3 部屋かは問わない。

根拠は現場での観察である。

- Object Capture は **2〜3 部屋ぶんを一度に処理できる**。部屋単位に切る必要は無い
- **異なる部位の写真が紛れても、計算に使えない写真は API 側が除外する**
- 分割したモデル間の**重複は多いほうが良い**（合成の対応点が増える）

### 1.2 指針 1: 混入のコストは分断のコストよりはるかに小さい

旧設計は暗黙に逆を仮定していた（「無関係な写真を持ち込むぶん有害」）。向きが
逆になるので、迷ったときの倒し方が全部変わる。

| 迷ったとき | 旧 | 新 |
| --- | --- | --- |
| この写真を入れるか | 証拠が無ければ入れない | **入れる**（API が捨てる） |
| ここで切るか | 上限を超えたら切る | **切らない側に倒す** |
| 共有写真を何枚 | 15 枚（固定） | **塊の 30% 前後**（数十枚） |
| 判定できなかった組 | 保留（落とさない） | **そもそも判定しない** |

「判定できないなら判定しない」が要点で、#11 / #12 で費やしたコストの大半は
**答えが出ない問いに答えようとしたぶん**だった。

### 1.3 指針 2: 大域的な最適化を避け、失敗が局所に留まる方法を選ぶ

**これが今回いちばん高くついた学び**で、§6.3 の実測から来ている。

同じ「視覚特徴の近傍グラフ」を使っても、

- **大域的な並べ替え**（フィードラーベクトル）は、別の場所を結ぶ辺が
  **全体の 0.4% あるだけで全体が崩れる**（隣接一致 0.99 → 0.45）
- **局所的な窓の成長**は、同じ汚れをまったく受けない（混入率 0.000 のまま）

**失敗の形が違う。** 大域的な方法は「全部が壊れる」、局所的な方法は
「窓が 1 つ汚れる」。そして §1.2 のとおり、窓が汚れるのは安い。

### 1.4 指針 3: 判断を「画像の見え方」から「グラフの構造」へ移す

#11 / #12 が 2 度行き詰まった理由は、判断が**画像の見え方**に依存していたこと
だった（合成画像では検証できず、実写真は公開できない）。

新設計では、視覚特徴は**近傍を並べる**のにしか使わず、判断（どこで切るか・
何を入れるか）は**グラフの構造**が決める。したがって**写真を 1 枚も使わずに
`swift test` で固定できる**（§5.6）。

## 2. 設計の入力: 共視グラフ

### 2.1 作り方

```
写真 → 縮小（320 px・1 回のデコード）→ Vision の feature print
     → 相互 k 近傍グラフ（既定 k = 12）→ 共通近傍フィルタ
```

**閾値を持たない。** 距離の絶対値ではなく**順位**だけを使う。これは #11 が
失敗した理由への直接の回答で、実測でも順位は極めてよく効いている（§6.1）。

| | 上位 5 | 上位 10 | 上位 30 |
| --- | --- | --- | --- |
| 撮影順で隣り合う写真（±1） | **0.71** | 0.78 | **0.88** |
| 無作為 | 0.00 | 0.01 | 0.02 |

**相互**に上位へ入った組だけを辺にする。片側だけの近傍を採ると、ハブになった
1 枚が全体を繋いでしまう。

### 2.2 共通近傍フィルタ

**真に隣接する 2 枚は近傍を共有する**（同じ場所の前後を一緒に見ている）が、
別の場所の空似は共有しない。共通近傍が 2 本未満の辺を落とす。

合成グラフでの効果は明確で、**孤立した空似を 100% 除き、真の辺を 1 本も
失わない**（§6.3）。閾値を 1 つ持つが、これは**画素の見え方ではなくグラフの
構造**への閾値なので、合成グラフで挙動を固定できる。

### 2.3 EXIF はここに要らない

このグラフは**写真の画素だけ**から作る。EXIF が 1 枚も無くても成立する。
複数人での撮影・複数日にまたがる撮影・SNS 経由で EXIF が落ちた写真が、
すべて同じ経路で扱える。**EXIF の使いどころは §3.6 に限る。**

## 3. 設計: 窓の作り方

### 3.1 窓は「支持数の多い順」に育てる

種を 1 枚選び、**いまの集合へ何本つながっているか（支持数）が多い順**に
足していく。容量 `C` に達したら止める。

```
inside = {種}
繰り返し: inside への辺が最も多い写真を 1 枚足す（容量まで）
```

**空似に構成上強い。** 別の場所を結ぶ辺は 1 本しかつながらないので、本当の
続き（共視グラフでは 4〜8 本）に**必ず**負ける。確率ではなく構造からの帰結で、
実測でもそのとおりになる（§6.3）。

| グラフの汚れ | 幅優先の球 | **支持成長** |
| --- | --- | --- |
| きれい | 0.000 | 0.000 |
| 孤立した空似 20 本 | 0.406 | **0.000** |
| 孤立した空似 200 本 | 0.617 | **0.000** |
| かたまりの空似 4 組 | 0.252 | 0.248 |

（混入率＝窓の中心から窓幅ぶん以上離れた写真の割合）

**幅優先では駄目**なのが要点。ワームホールを 1 本通った瞬間に、遠くの領域が
丸ごと入ってくる。

### 3.1.1 これは「グラフの上の領域拡張法」である

対応は素直だが、**判定基準だけが決定的に違う**。

| | 画像の領域拡張法 | この設計 |
| --- | --- | --- |
| 種 | 画素 | 写真 |
| 近傍 | 格子（4/8 近傍・**与えられる**） | 共視グラフ（**特徴量から作る**） |
| 追加の判定 | **似ているか**（輝度差の閾値） | **何本つながっているか**（支持数） |
| 停止 | 均質でなくなったら | **容量**（Object Capture の上限） |
| 出力 | 分割（partition） | **被覆（cover・わざと重ねる）** |

**古典的な領域拡張の判定基準を使っていたら確実に失敗する。** 「似ているものを
足す」ので、同じ建具・同じ壁紙の別の部屋が真っ先に入る — #11 が失敗した形その
ものである。支持数は**似ている度合いを一切見ない**ので、この罠に落ちない。

系譜としては**局所グラフクラスタリング / シード集合の拡張**（Andersen–Chung–Lang
の局所分割など）に当たり、**計算も誤差もその塊の中で完結する**。§7.3 で棄却した
大域的なスペクトル法のちょうど局所版で、§1.3 の指針の上に両者がきれいに並ぶ。
支持数で足すのは「集合から外へ出る辺を最も減らす頂点を貪欲に足す」ことと同じで、
グラフ分割の古典的な貪欲法と同じ発想である。

#### 領域拡張の既知の弱点は、そのままこちらの弱点でもある

**(1) 種と順序への依存 → 決定的な順序を仕様に含める。**
支持数が同数のときの順序を決めておかないと、同じ入力で結果が変わる。§7.1 で
Louvain を「同じ入力で結果が変わるツールは調整の手がかりを失う」として退けた
以上、こちらも同じ基準を自分に課す。**同数のときは、共視グラフの辺の重みの
合計が大きいほう → それも同じなら安定した識別子順**とし、**乱数を使わない**。

**(2) 漏れ出し（leakage）→ 窓の「閉じ具合」を診断に出す。**
領域拡張の古典的な失敗は、境界が 1 画素弱いだけで隣の領域へ漏れることだった。
支持成長は 1 本の辺では漏れないが、**どこで止めたか**は依然として知りたい。

そこで**コンダクタンス**（窓から外へ出る辺の割合）を manifest に出す。
**停止条件にはしない**（停止は容量が決める）が、指標としては無料で得られる。

| コンダクタンス | 意味 | 打つ手 |
| --- | --- | --- |
| 低い（閉じている） | 自然な切れ目で切れている | そのままでよい |
| 高い（開いている） | 密なところを無理に切っている | **その境界の重なりを増やす** |

**重なりを増やすべき箇所が manifest から分かる**ようになるのが利点で、
§3.3 の「重なりが足りない対には育て足す」の判断材料そのものになる。

### 3.2 種の選び方と、全体の覆い方

1. まだどの窓にも入っていない写真から、**次数の高いもの**を種にする
   （孤立した写真から始めると窓が痩せる）
2. 容量まで育てる
3. **すべての写真がいずれかの窓に入るまで繰り返す**

**`_unassigned` は原理的に空になる。** 「小さすぎるグループの吸収」も要らない
（最後に残った少数は、最も強く繋がる窓へ足す）。

### 3.3 重なり: 分割ではなく被覆（cover）

**塊をきれいに切り分けてはいけない。** 隣り合う窓には同じ写真を入れる。

- 種を**既存の窓の縁から**選ぶと、育てた窓は自然に前の窓と重なる
- 重なりが足りない対には、**互いの側へ育て足す**（既定で塊の 30%・下限 40 枚）

下限 40 枚には根拠がある。実測で**34 枚離れると視覚的に無関係になる**ので
（§6.1）、共有区間がそれより短いと「境界の両側から同じものを写している」
保証にならない。

**共有写真が実際に重なっていることを別途確かめる必要は無い。** 共有部分は
共視グラフ上で連結した塊なので、重なりは構成から従う。#11（Vision の位置
合わせ）も #12（画素相関）も、確かめようとしていたのはこの性質だった。

### 3.4 窓の中の並び —`sequential` の根拠

Object Capture の `sampleOrdering = .sequential` は「**与えた並びの隣どうしは
空間的に隣接している**」という**こちらからの宣言**である。EXIF とは無関係で、
**宣言を正しくする責任はこちら側にある。**

したがって並びは**その窓の中だけで**作る。

- 支持成長の到達順、または窓の中だけの局所的な並べ替え
- 窓は数百枚で空間的にまとまっているので、ワームホールが入る余地が小さく、
  入っても影響がその窓に閉じる

**大域的な並びは作らない**（§1.3・§7.3）。`sequential` は実測で効くことが
確かめられている（§6.2）ので、この根拠づけは実利に直結する。

### 3.5 Object Capture へ渡す設定（実測で決めた）

| 設定 | 値 | 根拠（§6.2） |
| --- | --- | --- |
| `featureSensitivity` | **`.high`** | 死んでいた区間が生き返る。姿勢の付く枚数も増える（69 → 79〜87） |
| `sampleOrdering` | **`.unordered`**（§6.2.7 で訂正） | `sequential` は「並びの隣は空間的にも隣」という宣言で、支持成長の窓では嘘になる |
| `isObjectMaskingEnabled` | false（`--subject scene`） | 建物・部屋では前景の切り出しが破綻する |
| 品質フィルタ | **必須** | ブレの大きい下位 10〜25% を落とすと、どの設定でも死んでいた区間が通る |
| 1 窓の上限 | **1000 枚**（ハードウェア） | `PhotogrammetrySession.limits` |

**`.high` の代償は時間**で、`.normal` の 3〜4 倍（100 枚で 5〜9 分）。それでも
既定にする — 通らない窓があるより遅いほうがましだから（§1.2）。

### 3.6 通らなかった窓の扱い（**主経路は作り直し、梯子はフォールバック**）

**「この窓は通るか」は投げてみないと分からない。** 実測で、窓の中身の統計
（鋭さ・隣接距離・レンズの種類数）は成否とまったく相関しなかった（§6.2）。

**落ちた窓を救う主経路は、その窓をいじることではなく、直したグラフで窓を
作り直すことである**（§3.10）。窓は毎巡グラフから作り直されるので、隣の窓が
返した姿勢で辺が直れば、悪い窓は次の巡には存在しない可能性が高い。以下の梯子は
**それでも動かないときのフォールバック**、および**1 巡目に材料を作るための手**
として持つ。

したがって窓の計画は「作って終わり」ではない。

```
窓を作る → 投げる → error 6 なら分割して再試行 → 通った構成を記録
```

これは推測ではなく実測に裏付けられている。実データで **100 枚が駄目でも 30〜50 枚
なら通る**区間があった。`CoverPlan` に**縮めて再試行する**責任を持たせる。

**再試行は 3 段の梯子にする。**

| 段 | 手 | 実測の効き目（§6.2） |
| --- | --- | --- |
| 1 | `.normal` で投げる | — |
| 2 | **`.high` で投げ直す** | 落ちた 4 窓のうち **1 窓だけ**が救われた（07: 姿勢 92 枚） |
| 3 | **窓を割って投げ直す**（窓の中でもう一度支持成長） | 未測定 |

**2 段目の効き目は限定的**なので、`.high` を既定にしたうえで 3 段目まで用意する。
逆に言えば、**残った失敗は設定では動かない**（＝窓の中身の問題）と分かった。

**大きさは失敗の原因ではない。** 落ちた 3 窓のうち 1 つは 72 枚しかなく、しかも
**51 秒で位置合わせを諦めた**（通った窓は 649 秒かけている）。小さいから通る・
大きいから落ちる、ではない。**繋がりの薄い集まりは、小さくても落ちる。**

**どうしても通らない窓は名指しして報告する。**「黙って悪い結果を出さない」
（設計原則 §4.0）を果たすには、どこが駄目かを言えることが要件になる。

### 3.7 姿勢は本番と同時に取る

**`.modelFile` と `.poses` を同じセッションで要求する。** 段階ごとの実測から、
位置合わせが全体の **95%** を占め、メッシュとテクスチャは合計 2.5% しかない
（§6.2）。したがって「姿勢だけ安く求める」余地は無く、**本番のついでに取るのが
唯一正しい**。追加コストはほぼゼロ。

**モデルも同時に取れるが、ほぼ無料ではなかった**（§6.2.6 で訂正）。190 枚の窓では
メッシュ 552 秒 + テクスチャ 173 秒で**所要の 45%**。姿勢だけを要求した実測では
この 2 段が 5 秒で終わっていたので、**`.modelFile` を要求するとメッシュが本当に
作られる**（＝要求しなければ作られない）と読むのが自然である。それでも
**反復の途中経過を目で確かめられる**ようになる。姿勢の枚数は「繋がったか」しか言わないが、モデルは**何がどう繋がったか**
を見せる — 窓の中身が本当に 1 つの場所なのか、隣り合う窓が同じ場所を写して
いるのかは、開いて見るのがいちばん速い。`trial-clustering.sh` は既定で
`<state>/models/<ラベル>.usdz` へ書き出す。

得られる姿勢は 3 つに効く。

1. **合成（`merge`）の対応点そのもの**（写真の URL に紐づく）
2. **どの写真が実際に使われたか**の答え合わせ。**どの窓でも姿勢が付かなかった
   写真は「本当に使えない写真」**で、撮り直しを名指しできる
3. 繋がらなかった窓の検出 → §3.6 の再試行の材料

### 3.8 EXIF は最適化と検算にだけ使う

**EXIF が無くても仕分けは成立する**（§2.3）。そのうえで、あれば次に使う。

| 用途 | 使い方 |
| --- | --- |
| 計算量 | 全ペア距離が重い規模になったら、時刻の近い組を先に見る |
| 検算 | 窓の中の並びと撮影順が大きく食い違ったら、**どちらかが壊れている**印として報告 |
| 事前分割 | 機材・サブフォルダ・大きな時刻の断絶は、信じてよい強い境界 |
| 診断 | レンズの混在・撮影間隔の分布を撮り直しの材料として出す |

**バックボーンには使わない。** 実測で「時刻順に並べて `sequential` を名乗る」
のは、この現場がほぼ 1 本の連続撮影だったから通っただけであり、複数人が同時に
撮れば時刻順は交互に挟まって**むしろ有害**になる（§7.5）。

### 3.9 ループ閉じ込みと、別々の撮影の橋渡し

**一度離れて戻ってきた撮影**は、支持成長が同じ窓へ引き込めれば、そのループは
**1 回の再構成の中で Object Capture 自身が閉じる**。

引き込めなかった（容量を超えて遠い）場合だけ、`merge` へ渡す隣接として扱う。
失敗のコストは低い — 見落とせば合成のループ誤差が残る、誤検出すれば `merge` の
RANSAC が落とす。

**複数の撮影（別の人・別の日）が同じ場所を撮っている場合は要注意。** 合成の
対応点は「**同じ写真ファイル**が 2 つの窓に入っていること」から来るので、写真を
1 枚も共有しない 2 つの撮影は、同じ部屋を撮っていてもポーズグラフ上で繋がらない。
共視グラフはこの 2 つを自然に繋ぐ（見た目が近いので辺が張られる）ので、
**支持成長がまたいで育てば自動的に解決する**。またげなかった対は診断で名指しする。

### 3.10 Object Capture の結果をグラフへ返す（反復）

**この設計で唯一、辺の正しさを外から検証できる経路。** 共視グラフは見た目の
近さから作った**仮説**でしかなく、かたまりで似た別の場所（空似・§9-2）は構造
だけでは見分けられないことが実測で分かっている（支持数 4〜5 で堂々と窓へ入る）。
一方 Object Capture は、窓を 1 回処理するだけで**その窓の中のどの写真が幾何的に
一貫した 1 つの再構成に入ったか**を返す。**自前でできなかった幾何検証（§7.2 で
保留にした SIFT + RANSAC の役目）を、本番処理の副産物として受け取れる。**

窓 1 個ぶんの姿勢が返ってきたら、その窓の中に**両端がある辺**だけを見て直す。

| 窓の中の 2 枚 | 意味 | 辺の扱い |
| --- | --- | --- |
| 両方に姿勢 | 同じ再構成に入った ＝ 幾何的に繋がっている | **確定**（以後守る） |
| 片方だけ姿勢 | OC が両方を手にして、繋げなかった | **強い反証 → 取り除く** |
| 両方とも姿勢なし | どちらも落ちただけ | **情報なし（触らない）** |

**3 行目が要点。** Object Capture は一貫した最大の集合を **1 つだけ**返すので、
窓の中に繋がらない領域が 2 つあれば小さいほうは丸ごと落ちる。落ちた者どうしは
互いに正しく繋がっている可能性が高く、ここを消すと**本物の辺を失う**。同じ理由で、
**姿勢が 1 枚も返らなかった窓（error 6）からは何も学ばない** — 失敗の原因が辺に
あるのか設定にあるのか区別できないため。

**確定は反証に優先する。** ある窓で落ちた辺でも、別の窓で両端に姿勢が付いて
いれば繋がりの証拠がある（落ちたのは容量や露出など別の理由）。実装では反証集合
から確定集合を差し引いてから適用する。

これを回すと、窓の作り方は 1 回きりの推定ではなく**反復**になる。

```
共視グラフ（仮説）→ 窓 → Object Capture → 姿勢
      ↑                                    │
      └──── 確定と反証で辺を直す ←─────────┘
```

**収束の性質。** 辺は増えず、確定した辺は二度と消えないので、**辺の集合は単調に
減り、確定集合は単調に増える**。したがって有限回で止まる（停止するのは、新しく
反証される辺が出なくなったとき）。1 巡ごとに窓は「実際に繋がると確かめられた
辺」だけを辿って育つようになる。

#### 判定はどこまで届くか

**1 窓ぶんの姿勢では全体の 15〜20% の辺にしか判定が届かない**（実測）。
これは規則が「両端が同じ窓の中にある辺」にしか働かないためで、残りが正しいと
分かったわけではない（§6.2.2 で一度読み違えた）。

一方で、**窓は共視グラフから育てているので、辺の 9 割以上はどれかの窓の内側で
両端が揃う** — 実測のコンダクタンス（窓の外へ出る辺の割合）は 0.02〜0.09 だった。
したがって**全窓ぶんの姿勢が揃えば、判定はほぼ全体に届く**。

#### 落ちた窓はそのまま残るのか（**残らない**）

落ちた窓（error 6）はその窓の内側について何も返さない。しかし**窓は固定物では
なく、毎巡グラフから作り直される**ので、悪い窓が居座るとは限らない。逃げ道は
2 つある。

1. **襟は隣の窓が見比べる。** 実測で **24% の写真が 2 つ以上の窓に属する**
   （1084 枚が 1 個・272 枚が 2 個・63 枚が 3 個・5 枚が 4〜5 個）。落ちた窓の
   縁にある辺は、隣の窓が通れば判定される
2. **窓の構成そのものが変わる。** 種は「まだ覆われていない写真のうち最も遠い
   もの」、成長は「支持数の多い順」で、どちらも**現在のグラフ**から決まる。
   辺が変われば窓の切れ目も動くので、**同じ悪い窓が再び作られる必然性は無い**

**ただし脱出は自動ではない。** この手続きは**決定的**（乱数なし・同数なら添字の
小さいほう）なので、

> **その領域の近傍で辺が 1 本も変わらなければ、まったく同じ窓が再び作られる。**

つまり「悪い窓が消えるか」は、**修正がそこまで届いたかの関数**である。届かせる
経路が上の 1（襟）で、届かなければ 2 は起きない。実データでは **76% の写真が
1 つの窓にしか属さない**ので、落ちた窓の内側だけにいる写真は襟からの波及頼みに
なる。

**測り方は用意した。** `measure-ordering --compare-windows <前の巡の窓>` が、
前の巡の各窓に対していちばん近い今の窓との一致度（Jaccard）を出す。
**落ちた窓が「そのまま」と出るなら、修正がその近傍まで届いていない。**

この関係から、**§3.6 の梯子（`.high` → はぐれ抜きの芯 → 分割）は主経路ではなく
フォールバック**でよい。主経路は「直したグラフで作り直す」。ただし**1 巡目だけは
例外**で、そこで全窓が落ちると材料がゼロになり反復が始まらない。

**次数 0 の写真（実データで 155 枚）はこの反復では救われない。** 消す辺も
確かめる辺も無いからで、こちらは撮り直しの側の問題として別に扱う。

#### 何を見て収束を判断するか

| 見る数字 | 意味すること |
| --- | --- |
| 巡ごとの**除去率**（除去 ÷ 見比べられた辺） | 下がれば収束。上がるなら窓の作り方に問題がある |
| 除去された辺が**どの窓に集中するか** | 散っている窓に偏るなら、それが混入の正体 |
| **見比べられた辺の割合** | 判定がどこまで届いたか。分母を出さない報告は誤読を生む |
| **前の巡の窓との一致度**（`--compare-windows`） | 落ちた窓が作り直されたか、居座ったか |

**費用は 1 巡ぶんの再構成そのもの**（数時間規模）なので、実装では**任意**とし、
既定は 1 巡。**まず 1 巡目の姿勢を全部書き出しておき、必要になったときに 2 巡目を
回せる**形にする（`PoseSet` を manifest と同じ粒度で保存する理由）。

### 3.11 反復の回し方 — **1 巡につき、内部指標で最良の窓を 1 つだけ投げる**

§3.10 は「姿勢が返ったら辺を直す」という規則までしか決めていない。**実際に何を
どの順で投げるか**をここで決める。`scripts/trial-clustering.sh` がこの手順その
ものである。

```
窓を作る → 内部指標で順位を付ける → まだ投げていない最良の窓を 1 つ投げる
   ↑                                                    │
   └──────── 姿勢を累積し、辺を確定・除去して ←──────────┘
```

**全窓を投げてから作り直すのではなく、1 窓ごとに作り直す。** §6.2.5 で、
窓が作り直されるかは「修正がその近傍まで届いたか」と 1 対 1 だと分かっている。
1 窓ぶんの姿勢でも**その近傍の辺は直る**のだから、次の窓を選ぶ前に反映したほうが、
悪い窓を投げる回数が減る。1 回が数十分かかる以上、**投げる前に分かることは全部
使ってから投げる**。

**順位は辞書式にする。重みを付けて足さない。** 単位の違う数字を足した点数で
切る場所を選ぶのは #12 で棄却した形なので、自分にも同じ基準を課す。

| 順 | 見るもの | なぜ |
| --- | --- | --- |
| 1 | **連結**（窓そのものの最大連結成分が 1.00 か） | 繋がっていない窓は、1 回の再構成で繋がりようがない（§6.2.3） |
| 2 | **芯の成分**（3 コアの最大連結成分の割合）が大きい | 芯が太い＝細い繋ぎで付いた写真の寄せ集めではない |
| 3 | **支持数の中央値**が大きい | 1 枚ずつが強く結ばれて入った |
| 4 | **コンダクタンス**が小さい | 外へ漏れていない（自然な切れ目で切れている） |
| 5 | 窓の番号 | 同着を決定的に解く（§3.1.1-(1)） |

**すべてグラフから出た数字だけで、EXIF も画像の見え方も使わない**（§1.4）。

**この順位付け自体がまだ仮説である。** §6.2 で確かめたのは「窓の中身の統計
（鋭さ・隣接距離・レンズの種類数）は成否と相関しない」ことで、**グラフの構造が
予言するかどうかは測っていない**。したがって試行では**指標と結果を必ず並べて
記録する**（`ledger.tsv`）。連結 1.00 の窓と 1.00 未満の窓で通った割合が変わら
なければ、この順位付けには根拠が無いと分かる — **順位を使って選びながら、順位
そのものを検証している**。

同じ窓を二度投げない規則も要る（1 回が数十分なので）。

- 中身の集合が**同じ**窓（指紋が一致）は投げない
- 既に投げた窓と **Jaccard が 0.9 以上**の窓も投げない（ほとんど同じものに
  数十分は払えない。ここだけは打ち切りなので、飛ばしたことを必ず言う）
- **落ちた巡の次は窓を作り直さない。** 姿勢が 1 枚も返らなければ辺は 1 本も
  変わらず、成長は決定的なので**まったく同じ窓が出る**（§6.2.5 で実測）。
  作り直す計算そのものが無駄なので、前の巡の窓から次の候補を選ぶ

**終わり方は 3 つ。** ①投げていない窓がもう無い（＝**収束**。同じ窓しか出て
こない）②巡数の上限 ③時間の予算。②③は打ち切りなので、どれで終わったかを
必ず出す。

## 4. 処理の全体像

```
1. 走査・読み取り   写真 → 縮小 1 回 → 品質指標・知覚ハッシュ・feature print
2. 品質フィルタ     ブレの大きい下位 N% と重複を落とす（§3.5・必須）
3. 共視グラフ       相互 k 近傍 + 共通近傍フィルタ（§2）
4. 窓の生成         支持成長で育て、重なりを確保し、全体を覆う（§3.1〜3.3）
5. 窓の中の並び     窓ごとに局所的に決める（§3.4）
6. 出力             group-NN/ にハードリンク + manifest.json
7. 再構成           窓ごとに .modelFile + .poses（§3.5・3.7）
8. 再試行           error 6 の窓は縮めて作り直す（§3.6）
9. 反映（任意）     姿勢で辺を確定・除去し、3 へ戻る（§3.10）
10. 合成（merge）   共有写真の姿勢から相似変換（別文書 §5）
```

**1〜6 が `sort`、7〜8 が `process`、10 が `merge`。** 8 と 9 が新しく、`sort` と
`process` の間にループが入るのが従来との違い（§3.6・§3.10）。9 は既定では回さない
（費用が再構成 1 巡ぶんそのものなので）が、姿勢は常に書き出しておく。

### 5.6 テスト方針 — ここが今回いちばん大きな変化

| ケース | 期待 |
| --- | --- |
| 帯グラフ（真の順序が既知） | 窓が連続区間になる |

| 種の位置をずらす | 窓の中身は変わるが、被覆と重なりの保証は崩れない |

**結論が出たらこれを Swift のテストへ移す。**

`FeaturePrinter`（Vision）と `PhotoInspector`（ImageIO）は従来どおり
カバレッジ集計から除外する — **判断をその層に置かない**という約束でもある。

## 6. 実測の記録

**すべて現場の写真 1424 枚（2026-08-03）。** 出力はいずれも写真そのものを
含まない数値なので、そのまま共有して設計の判断に使える。

### 6.1 視覚特徴（`scripts/measure-ordering.swift`）

```
result=go step1=ok ratio=0.539 recall1@30=0.88 lift=39.2 ordering=exif foreign=2 n=1337
```

| 測ったもの | 結果 | 意味 |
| --- | --- | --- |
| 隣り合う写真の距離 ÷ 無関係な組 | **0.539** | 視覚特徴は場所の近さを反映している |
| ±1 が上位 30 件に入る割合 | **0.88**（無作為 0.02） | **順位は無作為の 39 倍効く** |
| 無関係の 90% に達する隔たり | **34 枚** | 重なりの下限の根拠 |

**隔たりごとの距離は単調に増える**（0.242 → 0.307 → 0.341 → … → 0.456、
無関係 0.450）。これは「歩けば離れる・離れれば重ならない」という撮影の物理
からの帰結で、現場固有の性質ではない。

現場の事実も分かった。

- EXIF 時刻あり 1337 枚 / なし 87 枚（うち 85 枚はファイル名に連番）。
  機種名・焦点距離・GPS がすべて欠けているのが 89 枚
- 撮影間隔は 96% が 5 秒以内。**5 分以上のギャップは 8 箇所だけ**
- 35mm 換算焦点距離が 14 種類混在（13mm が 413 枚 = 31%）

### 6.2 Object Capture の挙動（`scripts/measure-poses.swift`）

**窓が通るか通らないかの地図**（100 枚・`mode=poses`・数字は姿勢が付いた枚数）。

| start | normal/unordered | high/unordered | high/sequential | + ブレ除去 |
| --- | --- | --- | --- | --- |
| 0 | error 6 | **ok 87** | ok 79 | — |
| 150 | error 6 | error 6 | **ok 41** | — |

落ちるのは、この設計の「黙って悪い結果を出さない」に真っ向から反するので、

| 窓 | 投入（ブレ除去後） | 姿勢 | 結果 | 位置合わせに費やした時間 |
| --- | --- | --- | --- | --- |

1. **`.high` への引き上げは 4 窓中 1 窓しか救わない。** 効くが足りない

2. **残る失敗は設定では動かない。** 窓の中身の問題であることが確定した

#### 6.2.2 姿勢をグラフへ返した 2 巡目（§3.10 の初回実測）

| | 本数 |
| --- | --- |
| 共通近傍フィルタ後の辺 | 4265 |
| **確定**（両端に姿勢） | 635 |
| **除去**（片方だけ姿勢） | 19 |

**残りの 3611 本を「両端とも姿勢が付かなかった辺」と読んではいけない。**
規則が働くのは**両端が同じ窓の中にある辺だけ**で、それ以外は
**見比べてすらいない**。窓 1 個は全体の 1/7 ほどしか含まないので、
数窓ぶんの姿勢では大半の辺に判定が届かない。

したがってこの数字から言えるのは 1 つだけである。

> **見比べられた範囲では、97%（635/654）の辺が確定した。**

分母を出さずに「辺はほぼ正しかった」と書くと、**見ていない辺を正しいと言った
ことになる**。実際に一度そう書きかけたので、`measure-ordering` の出力側にも
「見比べられた辺」の本数と割合を必ず出すようにした。

**反復の値打ちは、窓を回した数に比例して増える。** 全 15 窓ぶんの姿勢が揃って
初めて、グラフ全体に判定が行き渡る。

**別の入口からの手掛かり: 次数 0 の写真が 155 枚（11%）。** これは姿勢とは無関係に
グラフだけで分かる事実で、**どの窓へ入れても繋がりようがない写真**がこれだけ
あることを意味する。姿勢が付かない写真の少なくとも一部はこれで説明が付く。

#### 6.2.3 窓が内部で分断されるのは、はぐれを入れているから

2 巡目の窓の内部指標で「最大成分」が 0.48〜0.62 に落ちる窓があった。

**この列だけでは分断の証拠にならない。** 当時の実装は**3 コアに削ってから**
最大連結成分を測っていたので、周辺の写真（内部次数 3 未満）が剥がれるだけでも
下がる。**そこで「窓そのものの最大連結成分」を別の列（`連結`）として足した。**
測っていないものを根拠にしない、というだけの話だが、実際に一度これで誤った
結論を書きかけた。

そのうえで、**分断が起きるとしたら原因は構成上ひとつに特定できる。** 支持成長は
**支持数 1 以上でしか写真を足さない**ので、**育てた部分はグラフ上で必ず連結**で
ある。したがって

> **`連結` が 1.00 未満なら、その差はすべて後から入れた「はぐれ」**

が成り立つ（はぐれのうち窓の誰ともグラフで繋がらないものが、そのまま差になる）。
はぐれの吸収は、**この設計で唯一「画像の見え方」だけで判断している場所**
（§1.4 の原則から外れている唯一の場所）であり、そこがそのまま弱点になっている。

そこで窓と一緒に**はぐれを外した「芯」**を `core/` へ書き出す。芯は
「1 回の再構成で繋がるはず」と言い切れる唯一の集合なので、**落ちた窓の原因が
はぐれなのか中身そのものなのかを、往復せずに切り分けられる**（§3.6 の梯子で、
分割より先に試すべき手）。

| 芯を投げた結果 | 読み方 | 次の手 |
| --- | --- | --- |
| 芯は通る・窓は落ちる | **はぐれが窓を殺している** | はぐれを窓へ入れない（別扱いにする） |
| 芯も落ちる | 中身そのものが繋がっていない | 分割（§3.6 の 3 段目）→ それでも駄目なら撮り直し |
| 両方通る | はぐれは無害 | いまのままでよい |

**次数 0 の写真をどう扱うかは未決**。窓へ入れれば被覆は保てるが窓を汚す。
入れなければ被覆が壊れる代わりに「撮り直しの候補」として名指しできる。
**芯と窓の両方を投げた結果で決める。**

#### 6.2.6 支持成長の窓 1 個ぶんの実測（190 枚・姿勢 180 枚）

**この設計にとっていちばん良い数字が出た。** 支持成長で作った 212 枚の窓
（ブレ除去後 190 枚）を投げて、**180 枚に姿勢が付いた（94.7%）**。撮影順で切った
窓は 100 枚中 24〜87 枚だった（§6.2）ので、**共視グラフから作った窓のほうが
はっきり良い**。

| 段階 | 開始（秒） | その段階に費やした時間 | 割合 |
| --- | --- | --- | --- |
| preProcessing | 17 | 11 | 1% |
| imageAlignment | 28 | **791** | **49%** |
| pointCloudGeneration | 819 | 73 | 4% |
| meshGeneration | 892 | **552** | **34%** |
| textureMapping | 1444 | 173 | 11% |
| optimization | 1617 | 13 | 1% |

**§6.2 の「位置合わせが 95%・メッシュとテクスチャは 2.5%」は、モデルを要求して
いなかったときの数字だった。** 要求すると 45% がメッシュ側へ行く。姿勢だけが
目的の巡では `--no-models` で半分近く縮む。

**点群は 133,347 点**（2.0MB）。可視点集合による共視の判定に十分な密度がある。
`.pointCloud` の追加コストは 73 秒（4%）で、これは事実上無料と言ってよい。

**点群と姿勢は同じ座標系に乗っている。**

```
点群の範囲 (-7.11, -0.85, -8.23) 〜 (7.30, 3.48, 7.40)  対角 21.70
カメラの範囲 (-5.92, 0.86, -5.45) 〜 (3.13, 1.99, 5.17)  対角 14.00
カメラから点群の中心まで: 中央値 3.80（点群の対角の 18%）
カメラ座標系での点: 前方（-Z）71%・後方 28%
前方の点の光軸からの角度: 中央値 44°・下位 25% 30°
```

無関係な座標系なら前後は半々になるはずで、実際は 71:28。尺度も「21.7 m の場面を
3.8 m の距離から撮る」という撮影として無理がない。**モデル側が正規化されている
心配は無い。**

**ピーク物理フットプリントは 14.4GB**（190 枚）。窓の容量を上げるときはここが効く。

#### 6.2.7 `sampleOrdering` は `unordered` にする（§3.5 の訂正・A/B で実測）

**同じ窓（190 枚）で ordering だけを変えて比べた。**

| | `sequential` | `unordered` |
| --- | --- | --- |
| **姿勢** | 180 枚 | **183 枚**（skipped 10 → 7） |
| **位置合わせ** | 791 秒 | **800 秒**（+1%） |
| ピークメモリ | 14.4GB（モデル込み） | 4.7GB（モデル無し） |
| 点群 | 133,347 点 | 129,367 点 |

**総当たりは速くも遅くもならず、姿勢は増えた。** `sequential` の宣言は、この窓では
何も買っていなかったことになる（買えるはずの候補ペアの削減が、所要に現れない）。
理屈（下記）と実測の向きが一致したので、既定を `unordered` にする。

**ただし n=1 で、しかも姿勢率の高い窓での比較である。** 別の窓（`r004-window-07`・
190 枚）でも `sequential` 177 → `unordered` 186 で同じ向きに出たが、**どちらも
通りやすい屋外主体の窓**だった。

**難しい区間については逆の可能性が高い**（§6.2.9）。§6.2 の「窓が成立する場所の
地図」を読み直すと、start=150 / 300 は **`high/unordered` では error 6・
`high/sequential` では通っている**。`sequential` は速度のヒントであるだけでなく、
**候補の対応付けを撮影順の近傍に限ることで、空似との誤対応を防いでいた**と読める。
**この点は未決**で、難しい区間で ordering を振り直すまで結論は出せない。

**同じ A/B で「モデルは無料ではない」も確定した。** `--models-out` を外すと
`meshGeneration` + `textureMapping` は **725 秒 → 8 秒**、ピークメモリは
**14.4GB → 4.7GB**。要求しなければメッシュは作られない。反復の燃料は姿勢と点群
なので、**モデルは目で見たい窓だけ後から作る**（`trial-clustering.sh` の既定を
「作らない」に変えた。投げた窓の一覧は残してあるので、後から同じ窓を再現できる）。

##### 理屈の側

§3.5 は `.sequential` を既定にしていたが、**支持成長の窓には根拠が移らない**。

`sequential` は「**与えた並びの隣どうしは空間的に隣接している**」というこちらから
の宣言で、Object Capture はそれを信じて総当たりの対応付けを省く。§6.2 でこれが
効いたのは**撮影順で切った窓**での実測であり、そこでは宣言が真だった。

窓の中の並びは共視グラフ上の幅優先（§3.4）なので、**枝が違えば並びで隣り合っても
空間的に遠い**。宣言が嘘になれば、**実際は重なっている 2 枚が並びの上で離れて
いるだけで対応付けられない**。分断は混入よりはるかに高い（§1.2）ので、確かな
根拠が無い限り総当たり側へ倒す。

#### 6.2.8 `--grow-full`: 指標は上がったが、結果は落ちた

**窓の成長で被覆を見ない規則**（§3.1 の 2 段階をやめ、全写真から容量まで育てる）を
入れて比べた。動機は「先に育った窓がその領域の良い写真を先取りし、後の窓が痩せる」
という観察で、実際に同じ領域の窓が巡を追って **212 → 164 枚・芯の成分 0.92 → 0.79**
と痩せ、error 6 になっていた。

**窓の指標は劇的に良くなった。**

**それでも 3 窓とも error 6 だった。**

#### 6.2.9 内部指標は成否を予言しない。撮影順の塊は予言する

**§3.11 の順位付けは、実データでは反証された。**

1. **屋内は Object Capture でそもそも再構成できるのか。** 撮影順に連続した 100 枚

   空似を集めている」、落ちればこの現場の屋内は設定を含めた別の問題
2. **撮影順を証拠として使うか。** §2.3 は「EXIF はここに要らない」と書いているが、

   順位付けにだけ使うか、使わないかは方針の判断**であり、この文書では決めない。
   台帳（`ledger.tsv`）には塊の列を残してあるので、証拠は貯まり続ける

#### 6.2.11 除去された辺は痩せの原因ではない（算数）

窓が痩せた原因として「フィードバックの除去が真の辺を削っている」を疑ったが、
**5 巡ぶんの除去は合計 181 本 / 4284 本 = 約 4%** で、窓が 212 → 164 枚（−23%）に
痩せる説明にはならない。除去の規則（片方だけ姿勢 → 辺を落とす）は「OC が両方を
手にして繋げられなかった」という観測そのままで、疑うべき所ではなかった。

なお**反復の機構そのものは動いている**。

| 巡 | 見比べられた辺 | 確定 | 除去 | 除去率 |
| --- | --- | --- | --- | --- |

#### 6.2.12 Object Capture の API が返すもの（実機の SDK で確認）

```swift
public struct Pose {                        // macOS 14+
  public let translation: SIMD3<Float>
  public let rotation: simd_quatf
  public var transform: Transform { get }
}
case pointCloud                              // Request（macOS 13+）
case pointCloud(PhotogrammetrySession.PointCloud)   // Result
public struct PointCloud { public let points: [Point] }  // position + color
```

- **投影行列（内部パラメータ）は返らない。** `intrinsics` / `calibrationData` は
  `PhotogrammetrySample`（**入力**側・macOS 15+）にあり、こちらから渡すことは
  できても OC の推定値は読めない。共視の計算に要る内部パラメータは、EXIF の
  35mm 換算焦点距離から自前で組む（測量ではないのでこの精度で足りる）
- **点群は同じセッションで取れて、事実上無料**（73 秒・全体の 4%）。密度は
  55,000〜133,000 点で、可視点集合による共視の判定に十分
- **点群と姿勢は同じ座標系**（前方 65〜71%・後方 28〜34%。無関係なら半々。
  カメラから点群中心まで対角の 16〜18% で、撮影距離として無理がない）
- **視錐台の重なりだけでは共視にならない。** 壁を挟んだ 2 枚は錐台が交差しても
  何も共有しない。遮蔽まで見るには点群（またはメッシュ）が要る

**回転と点群は毎回書き出している**（`poses.tsv` に `qx qy qz qw`、
`points/<ラベル>.points.bin`）が、**まだ判定には使っていない**。現在の
フィードバックは「姿勢が付いたか」の 1 ビットだけである。

#### 6.2.4 測定結果を汚す既知の故障（ML モデルキャッシュ）

2 巡目の実行中に次が出た。

```
E5RT encountered an STL exception. msg = MILCompilerForANE error:
failed to compile ANE model using ANEF. Error=_ANECompiler : ANECCompile() FAILED.
```

**これは `ModelCache`（`Sources/PhotogrammetryCore/ModelCache.swift`）が既に
名指ししている故障**で、写真にも設定にも原因が無い。壊れたバンドルが残ると
以降は毎回同じところで落ちるので、**これが出た後の窓の成否は測定として信用
できない**。`~/Library/Caches/<実行体名>/com.apple.e5rt.e5bundlecache` を消して
から測り直す。

**測定の道具にも同じ判定を入れる**（`ModelCache.isCompilationFailure` と同じ
文字列を見る）。黙って「error 6 が増えた」と記録してしまうのが最悪だから。
`measure-poses` は場所を毎回ヘッダに出し、`--purge-model-cache` で消せる。

**この故障が出る前に取れた値**: 2 巡目の窓 01 は **182 枚に姿勢**（投入 208・
うち 8 枚は skipped）＝ **87.5%**。この 1 件だけは有効。

#### 6.2.5 辺が変われば窓は作り直される（合成データ・`--compare-windows`）

**「落ちた窓は次の巡には無いのではないか」を直接確かめた実験。** 同じ写真集合で
窓を 2 回作り、前の巡と一致度（Jaccard）を比べる。

| 条件 | 前の巡と同じ窓 |
| --- | --- |
| **フィードバック無し**で作り直す | **6 / 6 個がそのまま**（一致度 1.00） |
| **姿勢を反映**して作り直す（辺 24 本除去） | **5 / 6**。**辺が消えた領域の窓だけ**が作り直された（0.64） |

**両方の主張が同時に正しい。** 辺が直れば窓は作り直され、届かなかった領域は
**1 枚も違わず同じ窓が再生される**（成長が決定的なので当然だが、実際にそうなる）。
つまり

> **窓が作り直されるかは、修正がその近傍まで届いたかと 1 対 1 で対応する。**

同じ実行で、**窓 2 個ぶんの姿勢では判定が全体の 34.1% に届き、除去は 24 本**
だった（窓 1 個なら 19.7%）。**判定の届く範囲は窓の数に比例して伸びる。**

### 6.3 大域的な並べ替えの失敗と、その切り分け

**実データ**（相互 12 近傍・辺 5128 本・連結成分は実質 1 個）。

| 並び | 隣り合う組の距離（中央値） |
| --- | --- |
| 撮影順（EXIF） | **0.242** |
| **フィードラー並べ替え** | **0.388** |
| 無関係な組 | 0.450 |

**ほとんど無作為と変わらない。** 撮影順との一致は 13%。

**真の順序が分かる合成グラフで切り分けた**（`scripts/simulate-seriation.py`）。

| グラフの汚れ | 隣接一致 | 共通近傍フィルタ後 |
| --- | --- | --- |
| きれい | **0.99** | 0.99 |
| 孤立した空似 20 本（全 5356 本の **0.4%**） | **0.45** | **0.99** |
| 孤立した空似 200 本 | 0.22 | 0.99 |
| **かたまりの空似 4 組** | 0.70 | **0.70**（効かない） |

**理論も実装も正しく、方法そのものが脆い。** フィードラーベクトルは大域的な
最適解なので、別の場所を結ぶ辺が 1 本あるとワームホールになって線全体が
組み替わる。**現場固有ではなく方法の性質**で、どんな建物にも同じ壁・同じ建具は
あるので避けられない。

窓の育て方の比較は §3.1 の表のとおりで、**支持成長は孤立した空似に構成上
影響されない**。かたまりの空似は残るが、混入率 25〜32% で**窓が汚れるだけ**に
留まる。

### 6.4 次に測ること

| 測ること | 何が決まるか |
| --- | --- |
| **支持成長で作った窓を Object Capture へ投げる** | 設計全体の合否。EXIF 無しで作った窓が通るか |

| **姿勢を返して作り直した 2 巡目の窓**（§3.10） | 反復に意味があるか。1 巡目より姿勢率が上がるか・窓の数が減るか |

### 6.5 測定の道具（現在の状態）

**本実装の前に、この 2 本のスクリプトで設計を確かめている。** どちらも
`swiftc <ファイル> -o <名前>` で単体ビルドできる（SwiftPM のターゲットではない）。
Linux のリモートセッションからは動かせないので、**変更したら ci-debug の
`mode=shell` でコンパイルと動作を確かめてから利用者へ渡す**（CLAUDE.md の
「CI デバッグ」節）。

#### `scripts/measure-ordering.swift`（写真 → グラフ → 窓。GPU 不要）

| オプション | すること |
| --- | --- |
| `--windows N` | 容量 N で支持成長し、`window-NN.txt` を書き出す（§3.1） |
| `--window-dir DIR` | 書き出し先。`split/`（半分に割った案）と `core/`（はぐれ抜き）も作る |
| `--neighbours K` | 相互 k 近傍の k（既定 12） |
| `--overlap-ratio R` | 段階 1 の枠（既定 0.3。§3.1 の襟） |
| `--feedback DIR` | **姿勢で辺を確定・除去する**（§3.10）。`*.poses.tsv` を読む |
| `--compare-windows DIR` | **前の巡の窓と一致度を比べる**（§6.2.5） |
| `--seriate K` / `--segments N` | 棄却した案の再検証用（§6.3） |
| `--cache FILE` | **視覚特徴とブレ指標を残して次回は読み直さない**。反復では毎巡ここを通るので、1424 枚の読み取り（数分）が 2 巡目以降ほぼゼロになる |

次に投げる窓を選ぶのに使う。**表を目で読んで選ぶ作業を自動化するためだけのもの**
で、判断は増えていない。

EXIF は毎回読み直す。写真の同一性は大きさと更新時刻で見て、**再利用した枚数と
読み直した枚数を必ず出す** — 黙って古い値を使っていたら測定そのものが信用でき
なくなる。

## 7. 検討して採らなかった案

**採らなかった理由を残すのは、同じ道を二度通らないため。**

### 7.1 Louvain / Normalized Cut によるコミュニティ抽出 — **不採用**

提案された手順の第 3 段。**仮に完璧なシーングラフがあっても正しい答えを
出さない。**

- **容量制約が入らない。** 実際の制約は「1 塊 ≤ N 枚」だが、モジュラリティ
  最大化にはそれを表現する場所が無い。900 枚のコミュニティと 3 枚の
  コミュニティが並んで出て、結局そのあとに容量制約つき分割が要る
- **正規化カットは合成にとって最悪の場所で切る。** エッジが最も細くなる場所
  （ドアの前）は、**共有写真が最も少なくなる場所**であり、合成の相似変換が
  最も不安定になる。§1.2 の「重複は多いほど良い」と符号が逆
- 解像度限界（小さな部屋が隣へ吸収される）と縮退（同じ入力で結果が変わる）
- **そもそも部屋を見分けるのは要件ではない**（§1.1）

### 7.2 疎な特徴点マッチング + RANSAC（SIFT / ORB） — **保留**

写真測量の定石であり、原理は正しい。採らない理由は 4 つ。

1. **外部依存。** OpenCV は「外部依存を増やさない」方針と衝突する（署名・
   同梱・ユニバーサルビルドまで波及）。Vision は特徴点の記述子と対応付けを
   公開していないので、依存なしなら自前 600〜1000 行
2. **計算量。** SIFT の総当たりは 1 ペア 5 億 flop 規模で回らない。やるなら
   ORB（500 点・256 bit）一択
3. **平面退化。** 基礎行列は場面が平面に近いと不定になる。**白い壁の室内は
   まさにこの領域**で、H と F を当てて比べる（QDEGSAC）まで込みでないと、
   「もっともらしいが無意味な判定」を別の形で作る
4. **§1.2 のもとでは本体に要らない。** 効く場所があるとすれば §3.9 の
   ループ閉じ込みだけで、そこは失敗のコストが低い

**将来やるとしたら**: 自前 ORB + H/F 併用を、フェーズ 3 以降の任意機能として。

### 7.3 大域的なスペクトル並べ替え（フィードラー） — **棄却**

Robinson 行列の並べ替えは第 2 固有ベクトルで復元できる（Atkins, Boman &
Hendrickson 1998）という定理があり、この現場の実測（隔たりごとの距離が単調
増加）はその前提を満たしている。**それでも失敗した。**

理由は §6.3 のとおりで、**大域的な最適解であるがゆえに、0.4% の汚れで
全体が崩れる**。§1.3 の指針はここから来ている。

**残したもの**: 相互 k 近傍グラフと共通近傍フィルタは、支持成長でもそのまま
使う。無駄になったのは「大域的に並べる」という一段だけ。

### 7.4 二巡構成（1 巡目で姿勢だけ・2 巡目で本番） — **棄却**

「不確実な写真は複数の窓へ入れておいて、姿勢の結果で再クラスタリングする」
という考え方は魅力的だったが、**1 巡目が安くない**ので成立しない。

`.poses` だけを要求してもメッシュとテクスチャの段階は走り、そもそも位置合わせが
全体の 95% を占める（§6.2）。**飛ばせても浮くのは 2.5%。**

**残したもの**: 「姿勢で答え合わせをする」という発想自体は正しいので、
§3.7（本番と同時に姿勢を取る）と §3.6（通らなければ縮めて再試行）として
生かしてある。**二巡する必要が無かっただけ。**

### 7.5 EXIF 撮影順をバックボーンにする — **棄却**

実測では EXIF 順を `sequential` として渡すとよく通った。しかしそれは
**この現場がほぼ 1 本の連続撮影だった**からで、次の場合に破れる。

- **複数人が同時に撮る** → 時刻順は 2 人の写真が交互に挟まり、
  `sequential` の宣言が**嘘になる**。EXIF が無いより悪い
- 複数日・別機材・SNS 経由で EXIF が落ちた写真

**`sequential` は EXIF の話ではなく、こちらが与えた並びについての宣言である。**
宣言を正しくする責任はこちら側にあるので、並びは共視グラフから作る（§3.4）。

**残したもの**: EXIF は最適化・検算・事前分割に使う（§3.8）。

### 7.6 #11 の視覚クラスタリング / #12 の画素相関 — **棄却済み**

| | 何を測ろうとしたか | 実写真での結果 |
| --- | --- | --- |
| #11 | feature print の距離で「同じ場所」 | 97% が 1 か所に潰れ、証拠にならず |
| #12 ① | 位置合わせ後の画素相関 | 骨格の的中率 45% |
| #12 ② | ブロックごとの局所一致率 | 骨格の的中率 **1.1%**・93% の写真が孤立 |

**#11 の失敗の理由は今回はっきりした。** 順位はよく効く（§6.1）のに
`RoomClustering`（k 近傍の連結成分）が 97% を 1 か所にまとめたのは、
**k 近傍グラフが撮影の鎖をほぼ再発見しているから**。連続した歩き撮りでは鎖が
全体を貫くので、連結成分は必ず 1 つになる。**視覚の近傍グラフで部屋を割るのは
原理的に無理だった。** 逆に、近傍を数えるだけの用途（§3.1）には理想的である。

**#12 の失敗の理由**は「3 次元の場面を別の立ち位置から撮った 2 枚を揃える
2 次元の変換が存在しない」ことで、これは PR #12 に詳しい。

## 9. この設計が間違っているとしたら、どこか

1. ~~**【最大】支持成長で作った窓を、まだ Object Capture へ投げていない。**~~
   **投げた。12/15 が通り、EXIF を使わずに作った窓が実際に再構成できることを
   確かめた**（§6.2.1）。残る 3 窓は設定では動かず、割って試す段（§3.6 の 3 段目）
   が未測定。**この設計の合否そのものは越えた。**
2. ~~**かたまりの空似（doppelgänger）は、グラフの構造だけでは見分けられない。**~~
   **これが実データで最大の問題として表に出た**（§6.2.9）。通った窓は撮影順の
   5〜6 か所からまとまって来ており、落ちた窓は 11〜18 か所に散っていた。
   **白い壁ばかりの屋内では、見た目の近さが共視の証拠になっていない。**
   §3.10 の反復は機構としては動く（§6.2.11）が、**空似を減らせるかはまだ
   示せていない**。
3. **`maxPerGroup` の実用値が未確定。** ハードウェア上限 1000 は分かったが、
   200 / 300 / 500 でどう変わるかは測っていない。
4. **姿勢の付く割合が低い**（100 枚中 24〜87 枚）。窓の作り方で改善するのか、
   撮影の質で決まるのかが分かっていない。**§3.7 の「使えない写真の名指し」は、
   思ったより多くを指すことになる。**
5. **`.high` は 3〜4 倍遅い。** 1424 枚を 200 枚の窓 10 個で回すと数時間かかる。
   利用者が待てる範囲かは、実際に通してみないと分からない。
6. **複数人・複数日の現場を持っていない。** §3.9 の橋渡しと §7.5 の主張は、
   どちらもこの現場では検証できない。**そういう現場の写真が手に入ったら、
   まず `d(隣) < d(2 つ隣)` を見る**（成り立たなければ時刻順が交互に挟まっている）。
7. **次数 0 の写真（155 枚・11%）の扱いが未決。** いまは見た目がいちばん近い
   窓へ入れている（`はぐれ`）が、それは §1.4 の原則から外れている唯一の場所で、
   窓の連結性を壊している疑いがある（§6.2.3）。**`core/` を投げれば決まる。**
8. **反復が実際に収束するかは未測定。** 単調性から有限回で止まることは言えるが、
   「何巡で落ち着くか」「除去率が下がっていくか」は実データで見ていない。
9. ~~**内部指標（§3.11 の順位）が成否を予言するかは未測定。**~~ **予言しなかった**
   （§6.2.9）。連結 1.00 の窓は 4 回投げて 0 回成功、連結 1.00 未満は 12 回中 4 回。
   グラフの密さは、空似で密になった窓を高く評価してしまう。**順位付けは作り直しが
   要る。** 実データで対応したのは「撮影順の塊」だけだった。
10. **`sequential` を捨てた判断は、難しい区間では逆かもしれない**（§6.2.7 の但し
   書き）。A/B を取ったのはどちらも通りやすい屋外の窓で、§6.2 の地図では
   start=150 / 300 が `sequential` でしか通っていない。
11. **屋内が Object Capture で再構成できるかを、まだ単独で確かめていない。**
   通った 4 回はすべて屋外主体の窓だった。ここが確かめられるまで、
   **設計の合否は半分しか見ていない**。

## 10. 引き継ぎ（次のセッションへ）

**現在地: 反復の機構は動くが、窓の中身が屋内で信用できない。**
1424 枚の現場（屋内が多数・屋外もある）に対し、16 回投げて 4 回通った。

> **`docs/design-oc-only-covisibility.md` §16（引き継ぎ）を読む。**
> 視覚特徴を使わず **Object Capture だけ**で大域姿勢を作れるかを実測 4 回で
> 詰めた文書で、**この文書に直接効く結論が 4 つ**出ている。
>
> 1. **床は `N/(1−重なり率)` ≒ 1.4N（約 2.5 時間）。vision を使っても下がらない。**
>    窓の作り方が買うのは床への近づきやすさであって、床そのものではない
> 2. **窓は間引いてはいけない。** 全密度 190/324 枚は通り、1/3 間引きは 56 枚でも
>    427 枚でも error 6。**密度で完全に説明でき、枚数では説明できない**
>    （臨界密度 `f*` は 0.6〜0.7）
> 3. **「窓を単独で投げない」は成立する**（通った窓に異物を 41% 混ぜても姿勢 188・
>    error 6 なし）が、**被覆の局面では 1 姿勢あたり 3 倍高いので割に合わない**。
>    アンカーを使うのは「落ちた写真の分類」と「繋がらない塊の接続」の 2 か所だけ
> 4. **§10 の未決の 3 択（撮影順を使うか）に第 4 の選択肢**が出た —
>    **D: 窓の「引き方」に使い、証拠には使わない。** 確率論の下では、撮影順が
>    嘘だった区間は 300 秒払って次へ行くだけなので損害が有界になる
>
> **この現場は外部・内部・床下・小屋裏に分かれ、床下は完全に切り離されている**
> （撮影者の申告）。**成果物は 1 つのモデルではなく C 個のモデル ＋ 繋がらない
> 箇所の名指し**であり、これは品質の問題ではなく構造の事実である。

### 確かめた結果、**否定された**こと

1. **内部指標（§3.11 の順位付け）は成否を予言しない。** 連結 1.00 の窓は 4 回
   投げて 0 回成功、1.00 未満は 12 回中 4 回（§6.2.9）
2. **窓の痩せ（成長順の先取り）は主因ではない。** `--grow-full` で指標を大幅に
   改善しても、3 窓とも error 6（§6.2.8）
3. **`sequential` を捨てた判断は、難しい区間では逆かもしれない**（§6.2.7）

### いちばん確からしい診断

**白い壁ばかりの屋内では、見た目の近さが共視の証拠になっていない**（§6.2.9）。

- 通った窓は撮影順の **5〜6 か所**からまとまって来ている
- 落ちた窓は **11〜18 か所**に散っている
- `--grow-full` は支持数だけで容量まで育てるので**空似をより多く引き込み**、
  グラフの密さ（指標）を上げながら中身を悪くする

つまり §9-2 の「かたまりの空似」が、**この設計の最大の未解決**として表に出た。

### 次に走らせる 3 つ（優先順）

**1. 屋内はそもそも再構成できるのか**（約 10 分・これが最優先）

```bash
BIN=<state>/bin/measure-poses
$BIN <写真フォルダ> --starts 150 --counts 100 \
    --ordering sequential --sensitivity high --drop-blurriest 10 --timeout 1800
```

撮影順に連続した 100 枚（§6.2 の地図で `sequential` なら通った区間）。**通れば
「窓の作り方が空似を集めている」で確定**、落ちればこの現場の屋内は設定を含めた
別の問題になる。

**2. 同じ区間を `unordered` でも投げる**（比較）— `sequential` の効きが難しい
区間で出るなら、§6.2.7 の既定を戻す判断材料になる。

**3. 点群による共視の判定を入れる**（材料は既に貯まっている）

`poses.tsv` に回転が、`points/*.points.bin` に点群がある。各カメラから見える点の
集合を求め、共有率で辺を判定すれば、**いまの「姿勢が付いたか」の 1 ビットを、
本物の共視の判定に置き換えられる**（§6.2.12）。空似は「同じ窓で両方に姿勢が付く」
ので現在の規則ではむしろ確定に昇格してしまうが、**可視点を共有しないので除去
できる**。内部パラメータは EXIF の 35mm 換算焦点距離から組む。

### 方針の判断が要る点（この文書では決めない）

**撮影順を証拠として使うか。** §2.3 は「EXIF はここに要らない」と書いているが、
実データで成否と対応したのは撮影順の塊だけだった。選択肢は 3 つ。

| | 内容 | 代償 |
| --- | --- | --- |
| A | 使わない（現状） | 屋内で空似を集め続ける |
| B | **順位付けにだけ**使う（どの窓から投げるか） | 窓の中身は変わらない。無駄な投入は減る |
| C | **窓を作るのに**使う（時刻の近さを支持の証拠に足す） | #8 の失敗へ戻る危険。ただし #8 は「メタデータで分類」であって「撮影順を対応付けの手掛かりにする」ではない |

台帳（`ledger.tsv`）には塊の列を残してあるので、**どれを選んでも証拠は貯まり
続ける**。

### 試行スクリプトについて（次のセッションへの申し送り）

`scripts/trial-clustering.sh` は実データを通す過程で 4 つの誤りを踏んで直した。
**測定の道具が黙って嘘をつくのが、この試行でいちばん高くつく失敗**である。

1. `^window ` の行頭一致 — RealityKit の警告が改行なしで結果行に食い込み、
   **通った窓を落ちた扱い**にしていた
2. `--rounds` が巡の通し番号の上限だった — 続きから始めると**何もせずに終わる**
3. 窓の一覧を `cat` で繋いでいた — 末尾に改行が無いので**実在しないパス**ができ、
   被覆の分母が 1424 → 1431 になった
4. 小さすぎる窓を解体したあと付随配列を絞っていなかった — **支持数が 1 つずれて
   別の窓の値**を出していた

### 本実装へ進む条件

**まだ移してはいけない。** 以前は「窓が通れば §5 の実装計画へ」としていたが、
実データで**通るのは屋外だけ**で、屋内では窓の中身が信用できないことが分かった
（§6.2.9）。**空似の問題に答えが出るまで、`Sources/` へは何も移さない。**

移してよくなる条件は 2 つ。

1. **屋内の窓が通るようになる**（上の 1〜3 のどれかで道が付く）
2. **その判断が、写真を 1 枚も使わずに `swift test` で固定できる形になっている**
   （§5.6。共視の判定を点群でやるなら、点群と姿勢を与えたときの辺の確定・除去が
   純ロジックになる）

**測定用スクリプトは本実装後も残す**（同じ入力で同じ窓が出ることを比べる基準に
なるため）。

`scripts/simulate-seriation.py` の合成グラフの事例は、**そのまま `swift test` の
テストケースにする**（きれい / 孤立した空似 / かたまりの空似 の 3 種）。
