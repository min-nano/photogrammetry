# ロードマップ

**この文書が方針の唯一の現在地。** 個別の設計は各設計文書にあり、実測は
`docs/measurements.md` にある（事実と設計は分けてある）。

## 0. いまの立ち位置

自動で仕分ける（`sort`）方向は #11〜#17 で試し、**close した**。実測は
`docs/measurements.md` に事実として保存してある。要点は 2 つ。

- **順位としての視覚特徴は強い**（無作為の 39 倍）が、**閾値としては分離しない**
  （距離が狭い帯に潰れる）。白い壁ばかりの屋内で「かたまりの空似」が残る。
- **どの自動指標も Object Capture の成否を予言しなかった。** 唯一対応したのは
  「窓の写真が撮影順でいくつの塊に散っているか」だけだった。

したがって当面は**仕分けを人が与える**。写真は手作業でフォルダに分け、
プログラムは**それを前提に、確実に回して、失敗の原因を切り分ける**ことに集中する。

`docs/design-oc-only-sampling.md` §15 の計算がこの判断を支持している ——
運用に要求すべきなのは「**1 フォルダの枚数を上限以下にする**」1 つだけで、
フォルダの中でエリアが混ざっていても結果は落ちない。

## フェーズ A（当面・いま作るもの）: 手作業のフォルダを最後まで回す

**前提**: 写真は人が意味のあるフォルダへ分けてある。プログラムは仕分けを推測しない。

### A-1. 複数フォルダをまとめて処理する入口

いまの `process` は「1 フォルダ → 1 モデル」で、フォルダが 10 個あれば 10 回
操作することになる。数時間かかる処理を 10 回見張るのは現実的でない。

- **入力は「フォルダの集まり」**（親フォルダを渡すとサブフォルダが単位になる）。
- **1 つずつ順に実行し、途中で落ちても次へ進む。** 全部終わってから結果を集める。
- **中断と再開。** 数時間×フォルダ数なので、途中で止めて後から続けられること。
  終わったフォルダをやり直さない（成果物の有無で判断する）。
- **進捗は「フォルダ 3/10・この生成の残り約 30 分」まで出す。**
  段階と残り時間は既にある（`ProcessingStage` / フェーズ 0）。
- 語彙は `APICommand` に 1 か所だけ定義する（CLI・URL スキーム・GUI が同じ機能に
  届くという既存の規約）。

### A-2. 原因の切り分けを助けるエラーハンドリング

**いまは失敗がほぼ「エラー 6」に見える。** 実測（`docs/measurements.md` §3）で
分かっているとおり、同じ error 6 でも中身は違う。**区別して名指しする。**

区別すべきものと、区別できる根拠:

| 症状 | 見分け方（根拠は measurements.md） | 利用者に言うこと |
| --- | --- | --- |
| 入力が上限を超えている | 枚数を数える | 「1400 枚までに分けてください」 |
| 有効な写真が少なすぎる | 品質フィルタの除外率 | 「7 割がブレています。撮り直しです」 |
| 位置合わせで落ちた | `imageAlignment` の段で終わった | 「この写真群は繋がりません」 |
| 早く落ちた（257〜385 秒） | 所要時間（§3.8） | 同上。**中身の問題であって設定ではない** |
| ML モデルキャッシュの故障 | 既知の文字列（§5.1） | 「環境の問題です」＋自動復旧 |
| 一部だけ姿勢が付いた | 姿勢の枚数 / 投入枚数 | **どの写真が落ちたかを名指しする** |

**設計上の要点は 1 つ。** 判定は純ロジック（`ReconstructionDiagnosis` のような層）に
置き、エンジンからは「段階・所要・姿勢の枚数・OS のエラー文字列」という**事実だけ**を
上げる。判定をエンジンやヘルパーに書かない（テストできなくなるため）。

**落ちた写真を名指しできるようにする。** `--emit-poses` があれば「投入したのに
姿勢が付かなかった写真」の一覧が出せる。これは撮り直しの指示にそのまま使える。

### A-3. `merge`

フォルダを分けて別々に生成すると、**座標系がフォルダの数だけできる**。しかも
Object Capture の出力は実寸にならないので**スケールもフォルダごとに違う**。
取り込み側で 1 つずつ合わせるのは現実的でないので、合成は要る。

**確定している設計**（導出と検証の経緯は PR #2。実測値は `docs/measurements.md`
§3.14 / §3.15）:

| 決めたこと | 中身 |
| --- | --- |
| 求めるもの | **相似変換 7 自由度**（回転・並進・**一様スケール**）。depth の無い写真では出力が実寸にならず、セッションごとにスケールが違うため |
| 対応点 | **共有写真の姿勢**。`Poses.urlsBySample` で姿勢が元ファイルに紐づくので、両方に現れる写真の `translation` を突き合わせるだけで**対応点が無料で手に入る** |
| 解き方 | **Umeyama の閉形式** + **RANSAC**。3×3 の SVD は Jacobi 法で自前実装できるので**外部依存ゼロを維持**できる |
| 退化の検出 | **必須**。対応点が一直線に並ぶと解が一意に定まらない。特異値比を見て閾値以下ならエラーにする（黙っておかしな変換を返さない）。位置で解いて**カメラの向きで検算**する |
| 全体の配置 | 信頼度（インライア数）で重み付けした**最大全域木**で伝播。木に含まれない閉路の**ループ誤差を報告**する（最適化は後） |
| 出力 | **SceneKit による単一 usdz**（案 a）。メッシュは結合せず**配置だけ揃える**（部屋ごとに分かれたままレイヤ分けできる） |
| 退避先 | 案(c)**変換行列の JSON を出して取り込み側で配置**。案(b) 外部参照は**テクスチャが落ちる**ので採らない（§3.15） |

**実装上の注意**（実測から出たもの）:

- `SceneAssembler` は各グループのルートノードに **`group-01` 等の名前を明示的に
  設定する**（放っておくと Object Capture が書いた内部名が出る）。
- 取り込み側で名前に**サフィックスが付き `Geom` 中間層が挟まる**ので、
  振り分けは**前方一致**で行う。
- **繋がらないフォルダは繋がらないと名指しする**（黙って一部だけ出さない）。
  あるフォルダの生成が失敗すると、そのノードがグラフから欠けて全体が非連結になる。

**手作業でフォルダを分けるなら、隣り合うフォルダに同じ写真を数枚ずつ入れてもらう**
のがいちばん安い（`docs/design-oc-only-sampling.md` §14.4 の実測: 重複が無いと、
切り方が完璧でも境界のぶんだけ確実に失う）。共有写真の選び方には条件があり、
**視点が一直線に並ぶと変換推定が退化する**ので、立ち位置を変えた数枚にする。

**実寸化**（モデル上の 2 点と実測値を与えて全体スケールを決める）は同じ Umeyama で
できるが、**必須ではない**（取り込み先で 1 回スケールすればよい。合成によって全体が
1 つのスケールに統一されることが `merge` の実務上の価値そのもの）。後回しでよい。

## フェーズ B（次）: 撮影の側から可達性を与える

フェーズ A は「人が与えたフォルダを信じる」ところで止まっている。**フォルダを
作る手間そのものを無くす**のがフェーズ B で、方向は 2 つある。どちらも
「写真の並びが分かっている」状態を**撮影の時点で作る**という一点で共通している。

根拠は `docs/design-oc-only-sampling.md` §14 — **足りないのは連続性ではなく
可達性**であり、局所性を保つ切り方さえ与えれば 10000 枚が 10 回で終わる。

### B-1. ビデオからコマを抽出する

**評価は `docs/design-oc-only-sampling.md` §16 に済ませてある。** 要点だけ:

- コマ番号がそのまま並びになるので、**仕分けが不要になる**。
- **重なり半径 `k` が跳ね上がる**（写真の実測 `k ≤ 5` に対し 30〜100）。`k` は
  臨界密度の指数なので効き方が桁違いで、**間引いてよい権利が増える** ——
  コマ数が膨らむこと自体は問題にならない。
- **カメラを回したまま玄関を通れば、外部と内部が 1 つのモデルになりうる。**
  「1 つのモデルにならないのは構造の事実」が撮り方の問題に変わる。

作るもの:

| | 中身 | 層 |
| --- | --- | --- |
| コマの取り出し | AVFoundation（`AVAssetImageGenerator`）。**外部依存は増えない** | ラッパー（カバレッジ除外に足す） |
| **適応間引き** | 直前に残したコマから見た目が十分変わったら残す。判定は知覚ハッシュ距離（`ImageStatistics` に実装済み） | **純ロジック** |
| 窓切り | 間引き後の列を重なり付きの窓へ切る | **純ロジック** |

**時間で等間隔に間引いてはいけない**（立ち止まった区間が同じ場所で埋まる。
連続コマは視差がほぼ無く三角測量が退化する）。

**先に測ること**（実機でビデオを 1 本撮るだけ）:

1. 適応間引き後にブレで落ちる割合。**4 割を超えるなら撮り方（速度）の問題。**
2. `k`（間引き梯子）。**20 を超えていれば §16.2 の恩恵が丸ごと入る。**
3. 画質（同じ対象を静止画と比べる）。**ここだけは目で見るしかない。**
4. 玄関をまたいで外部と内部が 1 つになるか。

### B-2. 専用の撮影アプリ

ビデオより一段進んだ選択肢。撮影の時点で**並び以上のもの**を記録できる。

- **ARKit の `ARCamera.transform`**（VIO による姿勢）を撮影中に記録すれば、
  仕分けどころか**初期姿勢まで手に入る**。窓の切り方は 3 次元位置の空間分割になる。
- 露出・焦点距離を固定でき、**歩きながらのブレを検知してその場で警告できる**
  （不足が分かるのが帰社後では遅い、という問題が撮影中に解ける）。
- 「敷居で 2〜3 秒止まる」のような**守れたかを機械が判定できる指示**を、
  その場で出せる。

**ただしこれは別アプリ（iOS）になる。** このリポジトリの範囲を超えるので、
着手する場合は**受け渡しの形式を先に決める**（写真 + 姿勢の TSV を
`docs/measurements.md` §3.6 と同じ形で書き出すのが最も安い）。

## フェーズ C（保留）: 自動の仕分けへ戻る

**いま戻らない。** 戻る条件は次のどちらか。

- **フェーズ B が成立しない**（ビデオの画質が実用に足りない等）と分かったとき。
- **提案者の質を測る手段ができたとき。** 具体的には
  `docs/design-oc-only-sampling.md` §15.4 の測定 —— #17 が既に持っている
  **188 枚の姿勢**を正解として、知覚ハッシュの最近傍との一致率を数える。
  **GPU も新しい走行も要らない。** 一致率が 8 割を超えるなら自動仕分けは復活しうる。

`docs/design-oc-only-sampling.md` の `explore`（無作為抽出だけで成分を剥がす手順）も
ここに属する。**手作業のフォルダ分けをする限り要らない。**

## 依存関係

```
A-1 複数フォルダの入口 ─┬─→ A-3 merge ──→ B-1 ビデオ ──→ B-2 専用アプリ
A-2 エラーの切り分け  ─┘                     │
                                              └→（B が駄目なら）C 自動仕分け
```

A-1 と A-2 は独立に進められる。A-3 は A-1 の後（複数の出力が揃って初めて
合成する対象ができる）。

## 変えてはいけない前提

これまでに実測で確定していて、方針が変わっても動かないもの。

- **GUI からの生成は必ず別プロセス**（`CorePhotogrammetry` は `abort()` しうる）。
  フェーズ A は「落ちるフォルダがある」ことを前提に回すので、ここの価値が増す。
- **判断は純ロジックへ下ろす。** フレームワークを叩く層を足したら、カバレッジの
  除外にも同時に足す（`CLAUDE.md`）。
- **黙って悪い結果を出さない。** 繋がらないものは繋がらないと名指しする。
