# ANE モデルのコンパイル失敗を掘る

#11〜#14 で Object Capture を何度も試行する中で、次の失敗が繰り返し出ている。

```
E5RT encountered an STL exception. msg = MILCompilerForANE error:
failed to compile ANE model using ANEF. Error=_ANECompiler : ANECCompile() FAILED.
```

アプリ本体（main）は `ModelCache`（`Sources/PhotogrammetryCore/ModelCache.swift`）で
これを見分け、`~/Library/Caches/<バンドル ID>/com.apple.e5rt.e5bundlecache` を消して
作り直すことで復旧している。**それは対処であって原因ではない。** この文書は原因の
候補を 1 つずつ潰すための記録で、結論が出たものはここに書き足していく。

候補は 3 つあった。

| 候補 | 状態 | 根拠 |
| --- | --- | --- |
| Xcode が古い | **潰した**（が犯人ではない） | §1 |
| OS / デバイスと合っていない | **潰した**（範囲は確認済み） | §2 |
| メモリ不足 | **未決。実機で測る**（§3 のスクリプト） | §3 |

---

## 1. Xcode が古い

### 分かったこと

CI は 3 本のワークフロー（`build.yml` / `test.yml` / `ci-debug.yml`）すべてで
**Xcode 16.2（macOS 15.2 SDK）に固定**されていた。2026-08 時点の
[actions/runner-images](https://github.com/actions/runner-images) の中身は

| ランナー | macOS | 入っている Xcode |
| --- | --- | --- |
| `macos-15` | 15.7.7 | 26.3 / 26.2 / 26.1.1 / 26.0.1 / **16.4（既定）** / 16.3 / 16.2 / 16.1 / 16.0 |
| `macos-26` | 26.5.2 | **26.6（既定）** / 26.5 / 26.4.1 / 26.3 / 26.2 / 26.1.1 / 26.0.1 |

なので、16.2 は**既定より 3 世代前**を明示的に選び続けていたことになる。
GA の最新（macos-26 + Xcode 26.6）へ揃えた。ユニバーサル（arm64 + x86_64）の
リリースビルドが通ることは ci-debug で確認済み（`swift build -c release
--arch arm64 --arch x86_64` が成功）。

### ただし、これは犯人ではない

**ANE 用の ML モデルも、それをコンパイルする ANECompiler も、アプリではなく
OS の側にある。** `CorePhotogrammetry` が内部で使うモデルはアプリのバンドルに
入っていないし、コンパイルを走らせるのも E5RT（OS のランタイム）である。
したがって、どの Xcode でビルドしても**コンパイルされる中身は変わらない**。

SDK を上げる意味は「古い SDK にリンクした結果、実行時に別の互換経路へ入る」
という筋の可能性を、調査の変数から外せることに尽きる。**変数を 1 つ減らす
ための作業であって、これで直ると期待してはいけない。**

## 2. OS / デバイスのターゲット

### いま宣言しているもの

| どこ | 値 |
| --- | --- |
| `Package.swift` | `platforms: [.macOS(.v14)]` |
| `packaging/Info.plist` | `LSMinimumSystemVersion = 14.0` |
| ビルド | ユニバーサル（arm64 + x86_64） |
| README | 「macOS 14 以降」 |

macOS 14 を下限にしているのは `PhotogrammetrySession.Request.poses` と
`Output.requestProgressInfo`（進捗の段階・残り時間）が macOS 14+ だから
（`docs/design-preprocess-merge.md` §2）。宣言は 4 か所で揃っている。

### Object Capture 側の要件（Apple の言う下限）

- **Apple Silicon（M1 以降）**、または
- **Intel Mac + 16GB RAM + AMD GPU（VRAM 4GB 以上・レイトレーシング対応）**

満たすかどうかは `PhotogrammetrySession.isSupported` が答える
（`PhotogrammetryEngine.isSupported` で公開済み。GUI・CLI とも起動時に見る）。

### ここから言えること

**ANE の失敗が出ているなら、そのマシンは Apple Silicon である。** Intel Mac に
Neural Engine は無く、E5RT / ANECCompile の経路そのものが存在しない。つまり
「デバイスが要件を満たしていない」という筋ではない — 要件を満たしているからこそ
ANE 経路に入っている。

**残る「合っていない」は OS 側の新しさの向きだけ**（アプリが古い SDK に対して
リンクされている、OS のモデルとコンパイラの組み合わせに不具合がある、など）。
前者は §1 で外した。後者はこちらから動かせないので、**再現条件を細かく残すこと**
（§3 のスクリプトが `env.txt` に macOS のビルド番号まで書く）が唯一の手になる。

## 3. メモリ不足 — 実機で測る

3 つの候補のうち、**手元で振れる変数を持つのはこれだけ**である（写真の枚数を
減らせばメモリの山は下がる）。すでに実測されている山の高さは、

| 条件 | ピーク物理フットプリント |
| --- | --- |
| 190 枚・姿勢のみ | **4.7GB** |
| 190 枚・姿勢 + モデル（`reduced`） | **14.4GB** |

（`docs/design-loose-clustering.md` §6.2.7）。搭載メモリによっては、これは
十分に天井へ届く高さである。

### 測る道具

```
scripts/measure-ane.swift      1 回投げて何が起きたかを機械可読に吐くだけの実行体
scripts/trial-ane-memory.sh    枚数を振って繰り返し、表にする driver
```

```bash
# まず 1 周だけ回して、道具が壊れていないことを確かめる
scripts/trial-ane-memory.sh ~/Pictures/現場 --counts 40 --repeats 1

# 本番（一晩置く想定）
scripts/trial-ane-memory.sh ~/Pictures/現場 --counts 40,80,160,320 --repeats 3

# 逆向きの実験（**作業中の Mac ではやらない**）
scripts/trial-ane-memory.sh ~/Pictures/現場 --counts 160 --repeats 3 --ballast 0,16
```

### 設計で外せない点

1. **試行ごとに ANE キャッシュを消す。** ANE 用モデルのコンパイルは
   **キャッシュが空のときにしか走らない**。消さずに枚数を振ると、コンパイルは
   1 回目にしか走らず、2 回目以降の「成功」は「コンパイルが成功した」ではなく
   「コンパイルしなかった」を意味する。それを枚数の効果と読むと、**必ず
   「枚数を減らせば直る」という嘘の結論**になる（1 回目が多い枚数なら逆の嘘）。
   ここが測定の要で、driver の存在理由でもある。

2. **枚数を往復させる**（巡ごとに全部の枚数を 1 回ずつ）。同じ枚数を続けて回すと、
   温度・他のアプリ・キャッシュの育ち方といった時間とともに動くものが、枚数と
   見分けられなくなる。

3. **失敗した瞬間の段階とメモリを残す。** 「何枚で失敗したか」だけでは裏が
   取れない。E5RT の行が出た時点の処理段階・フットプリント・システムの空き・
   スワップ・メモリ圧レベルまで記録する（`trials.tsv` の `ane_at_*` 列）。
   山の頂上（`imageAlignment` など）で毎回出るならメモリ、前処理の入口で出るなら
   メモリではない。

4. **逆向きの実験を用意する**（`--ballast`）。枚数を減らして出なくなった、は
   「メモリが原因」の証明にならない（たまたま出なかっただけかもしれない）。
   わざと空きを潰して**失敗を呼び出せるか**まで見て初めて確定する。既定では
   使わない。

5. **E5RT の行は行頭に来ないことがある。** フレームワークは改行なしで書くので、
   こちらの 1 行の前に繋がって出る（`"E5RT …ANECCompile() FAILED.window
   name=… result=ok"` が実際に記録されている）。判定も抽出も**行頭で錨を
   打たない**こと。

### 出るもの

```
<out>/env.txt      macOS のバージョンとビルド番号・チップ・搭載メモリ・Xcode・空き容量
<out>/trials.tsv   1 試行 1 行（outcome / ane_marker / ピーク / 失敗時の段階 …）
<out>/logs/        1 試行ぶんの生ログとメモリの標本
```

最後に枚数 × 重しごとの表（試行数・ANE 失敗数・abort 数・ピーク・空きの最小）が
出る。**読み方も一緒に出る**ので、表だけ見て早合点しないこと。

### 結論を書く場所

測定が終わったら、その結果をこの節の下に追記する。「枚数の上限で防げる」なら
それは `SortRequest` / `APICommand` の `maxPerGroup` の既定を決める根拠になり、
「防げない」なら `ModelCache` の対処（消して作り直す）が唯一の手だと確定して、
**自動で消してやり直す**ところまで本体へ入れる判断ができる。

### 3.1 1 回目の実測（2026-08-06）— **測定として無効。ただし 1 つ分かった**

MacBookPro18,3（M1 Pro・16GB・macOS 26.5.2 25F84・Xcode 26.6）で、
40 / 80 / 160 / 320 枚 × 3 巡 = 12 試行。

| | 全 12 試行 |
| --- | --- |
| outcome | **error 6**（位置合わせ失敗） |
| 姿勢 | **0 枚** |
| ピークの段階 | **imageAlignment** |
| ピークメモリ | 1.1〜2.1GB（通る窓の実測は 4.7GB） |
| 所要 | 40 枚 8.6 秒 / 320 枚 190 秒（通る窓は 190 枚 800 秒） |
| **ANE キャッシュ** | **全 12 試行で空のまま**（`cache_after_kb=0`） |

**ANE モデルのコンパイルが 1 度も走っていない。** 見張りの TSV でも
`measure-ane` のキャッシュは 42 分間ずっと `bundles=0` だった。したがって
これは「再現しなかった」ではなく **「試せていない」**。

#### 分かったこと（これは収穫）

> **ANE モデルは `imageAlignment` より後の段階でしか要求されない。**

error 6 で終わる窓では ANE の失敗は**原理的に起きない**。§6.2.4 で
「2 巡目の実行中に出た」のとも整合する — 出るのは**十分先まで進んだ窓だけ**。
つまりこの故障を調べるには、まず**通る窓を用意することが前提**になる。

#### なぜ窓が全滅したか（道具の欠陥）

`measure-ane` は**ファイル名順**で先頭から N 枚を取っていた。機材や改名が
混ざると名前順は撮影順にならず、空間的に連続しない窓になる。設計文書自身が
「撮影順に連続した 100 枚でも場所によっては丸ごと error 6」と書いている条件で、
それより悪い切り方をしていた。EXIF の撮影時刻で並べるように直し、
`--window-file`（通ることが分かっている窓を直接投げる）を足した。

#### 同時に直したこと

- **`ane_compiled` 列**を driver に足し、**1 度もコンパイルが走らなければ
  集計で大きく警告して終了コード 3 で終わる**。これが無かったせいで、無効な
  測定を「再現しない」と読みかけた。**測定の道具は、答えていないことを
  自分で言えなければならない。**
- `invalid` / `skipped` / `unreadable` 列（error 6 が「繋がらない」のか
  「写真が読めていない」のかの区別）、iCloud 未ダウンロードの検出。
- 見張りの不完全判定の誤検出（OS 側のキャッシュが軒並み `incomplete=1` と
  出ていた。空のディレクトリを「壊れている」と数えていたため）。

#### 副産物として記録された環境

`analysis_cpu` の最大 **163.9%**（`mediaanalysisd` / `photoanalysisd`）。
測定中ずっと写真解析が回っていた。§4-D の状況証拠として残す（今回は ANE
コンパイル自体が走っていないので、効果は不明）。空きメモリの最小 68MB・
スワップ常時 1.5GB は、16GB のマシンとしては詰まっているほう。

## 4. メモリ以外の候補と、その調べ方

メモリ説（§3）は「手元で振れる変数がある」から先に測っているだけで、**筋の良さ
の順ではない**。ここでは他の候補を、機序・予測・調べ方・当たったときの対策の
4 点セットで並べる。

観測されている事実のうち、候補を絞るのに効くのは次の 2 つ。

- 故障の実体は「**manifest.plist の無い不完全なバンドルが残る**」こと。つまり
  **壊れた瞬間が必ず存在し**、E5RT の行はその後の実行で出る「症状」にすぎない。
- 一度壊れると**毎回まったく同じところで**落ち、キャッシュを消すと確実に直る。

したがって調査の第一目標は「E5RT の行を出すこと」ではなく、**壊れた瞬間を
押さえること**である。そのための見張りが `scripts/watch-ane-cache.sh`
（読むだけなので、生成や §3 の測定と同時に流してよい）。

### A. コンパイル中の中断がキャッシュを壊している（最有力）

- **機序**: ANE モデルのコンパイル中にプロセスが死ぬと（`abort()` / 時間切れの
  `cancel()` / Ctrl-C / GUI の強制終了）、書きかけのバンドルが manifest.plist の
  無いまま残る。以後その実行体は毎回そこで落ちる。
- **なぜ最有力か**: #11〜#14 は「落ちる・中断する」を大量に繰り返している。
  条件が揃いすぎている。さらに **`CorePhotogrammetry` の `abort()` 自体が
  この故障の原因になりうる**なら、「落ちる → キャッシュが壊れる → 毎回落ちる」
  という自作自演のループが回っていることになり、observed の「何度も出る」と
  よく合う。
- **予測**: 失敗は**前の試行が異常終了した直後**に集中し、枚数とは相関しない。
- **調べ方**: (1) 見張りを流して、壊れた瞬間の直前に何が死んだかを見る。
  (2) **わざと壊す**（1 分で終わる決定的な実験）—

  ```bash
  rm -rf ~/Library/Caches/measure-ane/com.apple.e5rt.e5bundlecache
  /tmp/measure-ane ~/Pictures/現場 --count 40 &          # コールドキャッシュから
  # 見張りが「ANECompilerService が動き出しました」と言った直後に
  kill -9 %1
  scripts/watch-ane-cache.sh --once                      # 不完全なバンドルが残ったか
  ```

  残るなら機序が確定する。残らないなら A は落ちる。
- **当たったときの対策**: 本体で「不完全なバンドルを見つけたら自動で消して
  やり直す」。判定（`ModelCache.isCompilationFailure`）は既にあるので、**自動化
  するかどうかの判断だけ**が残っている。ボタンを押させる必要はなくなる。

### B. 同じキャッシュへの同時書き込み

- **機序**: キャッシュはバンドル ID（無ければプロセス名）で切られる。同じ実行体を
  2 つ同時に走らせれば、**同じディレクトリへ同時に書く**。
- **予測**: 並列に走らせたときだけ出る。単発では出ない。
- **調べ方**: 見張りの `oc_procs` 列（生成・測定プロセスの同時数）。決定的に
  やるならコールドキャッシュから 2 本同時に投げる。
- **対策**: ヘルパーの起動を直列化する、または実行ごとに `TMPDIR` ではなく
  専用のキャッシュ場所を割り当てる。

### キャッシュの実際の階層（2026-08-06 に確認）

判定を書く前提なので先に置く。ci-debug の `watch-ane-cache.sh --dump` で
macOS 26.5.2 の実機の中身を見た。

```
<cache>/25F84/                                          ← OS のビルド番号
  <モデルのハッシュ>/model.milhash                       ← 印だけ（ANE 化されていない）
  <モデルのハッシュ>/<ハッシュ>.bundle/universal.bundle   ← コンパイル済みの実体
```

ここから 2 つ言える。

1. **最上位は OS のビルド番号で切られている。** 更新すれば別のディレクトリに
   なるので、古いバンドルが再利用されることはない → **§4-C はほぼ潰れた**
   （ビルド番号のディレクトリが 2 つ以上あれば更新の置き土産。見張りが数える）。
2. **健全なキャッシュにも `manifest.plist` は無い。** OS 側のキャッシュ
   （Spotlight・duetexpertd）を端から端まで探して 1 つも無かった。
   「`manifest.plist` が無い＝壊れている」は**誤り**で、見張りの最初の版は
   これで全部のキャッシュを不完全と誤判定していた。実機のエラーが
   `manifest.plist` を名指しするのは事実だが、**その不在は健全な状態でも
   起こる**ので、単独では判定に使えない。

いまは「`.bundle` があるのに中身が空」を不完全の印にしている。**これも
仮の判定**で、本物の故障を 1 度観測したら、そのときの形に合わせて直すこと。

### C. OS 更新で古いバンドルが無効になった

- **機序**: ANE のファームウェア／コンパイラが更新されると、以前のバージョンで
  作られたバンドルは読めない。作り直せばよいはずだが、失敗として出ることがある。
- **予測**: 「**ある日を境に**毎回出るようになった」。キャッシュの日時が OS の
  更新日より古い。
- **状態**: 上記の階層から**ほぼ潰れた**（キャッシュは OS ビルドごとに切られて
  いるので、古いバンドルが新しい OS で読まれることはない）。残るのは「更新前の
  ディレクトリが残っていて容量を食う」程度の話。
- **調べ方**（1 コマンド。いちばん安い）—

  ```bash
  sw_vers
  ls -lT ~/Library/Caches/*/com.apple.e5rt.e5bundlecache/
  ls -lT /System/Library/CoreServices/SystemVersion.plist   # OS 側の日付
  ```

- **対策**: 一度きりの事象なら対策不要（消せば終わり）。ただし**アプリの更新
  や OS 更新のあと 1 回目は捨てる**運用にする価値はある。

### D. 他プロセスが ANE を占有している

- **機序**: `mediaanalysisd` / `photoanalysisd`（写真ライブラリの解析）は ANE を
  長時間使う。特に iCloud 写真を大量に取り込んだ直後・充電中・アイドル時に走る。
- **予測**: **同じ操作なのに出たり出なかったりする**ことの説明になる。時間帯や
  「写真アプリを開いた直後」と相関する。
- **調べ方**: 見張りの `analysis_cpu` 列。A/B するなら、写真解析が走っていない
  状態（電源を外す・写真アプリを閉じてしばらく置く）と走っている状態で比べる。
- **対策**: こちらから止められる筋ではないので、当たった場合は「再試行で回避」
  （＝ A の対策と同じ自動リトライ）へ合流する。

### E. 引き金は枚数ではなく**モデルの種類**（設定）

- **機序**: コンパイルは**必要になったモデルごと**に走る。`detail` /
  `featureSensitivity` / `subject` を変えれば別のネットワークが要る。だから
  「2 巡目の途中で急に出た」が起こりうる（1 巡目とは違うモデルを初めて要求した）。
- **予測**: 特定の設定でだけ出る。枚数とは無関係。
- **調べ方**: 枚数を固定して `--sensitivity` × `--detail` × `--subject` を振り、
  毎回キャッシュを消す。`measure-ane` は既に全部オプションを持っている。
  あわせて**不完全に終わったバンドルの名前**を記録すると、どのモデルが落ちたかを
  名指しできる（見張りが出す）。
- **対策**: 当たれば「その設定を避ける」という具体的な回避策になる。§3 の
  メモリ説より当たったときの実入りは大きい。

### F. ディスクの空き・書き込み権限

- **機序**: キャッシュを書き切れなければ不完全なまま残る。過去に `sudo` で
  走らせたことがあれば、所有者が root になっていて以後書けない、もありうる。
- **調べ方**: `ls -ld ~/Library/Caches/*/com.apple.e5rt.e5bundlecache` と `df -h`。
  見張りが空き容量を毎回記録している。
- **対策**: 明白（空ける・所有者を直す）。

### G. Rosetta（x86_64 スライスで動いている）

- **機序**: `.app` はユニバーサルなので、親プロセスや起動方法によっては
  x86_64 スライスで立ち上がりうる。x86_64 プロセスからの ANE 経路は保証が無い。
- **調べ方**: 動いているプロセスで `sysctl sysctl.proc_translated`（プロセス内
  から見る）、または `ps` で PID を取って `file` / `lipo -info`。**GUI から
  起動されたヘルパー**が arm64 かどうかが本番の答えになる。
- **対策**: 当たれば `.app` の起動経路を直す（「Rosetta を使用して開く」が
