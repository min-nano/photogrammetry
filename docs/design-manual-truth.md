# 設計メモ: 手で作った正解を基準にする

**状態: 道具は動く。正解そのものはまだ無い（人の作業が要る）。**

`docs/design-loose-clustering.md` の §10 が「方針の判断が要る」として残した点と、
§9 の未解決の大半は、**答え合わせの基準が無いまま指標を足してきたこと**から
来ている。この文書はその基準を作る方法を決める。

| 章 | 中身 |
| --- | --- |
| §1 | **何を正解と呼ぶか**（窓ではなく場所ラベル） |
| §2 | **人の手順**（フォルダ規約・迷ったときの原則・所要時間） |
| §3 | 正解を汚さないための手当て（循環・偏り） |
| §4 | **何が測れるようになるか**（出力と、それが答える未解決） |
| §5 | **正解そのものを検算する**（Object Capture に投げる） |
| §6 | コマンド |
| §7 | この方法が間違っているとしたら、どこか |

---

## 0. なぜ要るのか

#11 から #14 までで、仕分けの手掛かりは次のように増えた。

| | 使った手掛かり | 実データでどうなったか |
| --- | --- | --- |
| #8 | 時刻・GPS・露出・知覚ハッシュ・フォルダ | 精度が出ない |
| #11 | ＋ 視覚特徴（feature print）とその閾値 | **分布に谷が出ず**、閾値を決められない |
| #12 | ＋ 画素の重なりの実測 | **実写真 1424 枚で反証**（棄却） |
| #13 / #14 | 共視グラフの構造だけを見る窓 | 16 回投げて 4 回。**屋内が通らない** |

失敗の中身はそれぞれ違うが、**進め方の失敗は 1 つ**である。

> どの指標が当たっているのかを判定する基準が無いまま、指標を足していた。

たとえば #11 の「視覚特徴の距離 0.31」も、#12 の「インライア率 0.3」も、
**その閾値で切ったときに何を間違えたのかを誰も数えていない**。数えるには、
「この 2 枚は同じ場所である」と言い切れる集合が要る。それを人が作る。

**そして正解ができると、判断の順序が逆になる。** いまは「指標を作る → 実データで
投げてみる → 落ちる → 別の指標を考える」で 1 巡が数十分から数時間かかっている。
正解があれば、**投げる前に指標を採点できる**。

## 1. 何を正解と呼ぶか

### 1.1 真実は 2 つあり、値段が違う

| | 何を言えるか | 取得コスト | 覆う範囲 |
| --- | --- | --- | --- |
| **T0 人の目** | この 2 枚には同じ面が写っている | 安い（1424 枚で 1〜2 時間） | **全数** |
| **T1 Object Capture の姿勢** | この 2 枚は幾何的に繋がった | 高い（1 窓で数十分） | 投げた窓だけ |

**T1 が本物の真実**である（設計 §3.10 の「繋がっているかどうかの正解は姿勢を
信じる」はこれ）。ただし T1 は全数には取れない — 全ペアを確かめるには全ペアを
再構成することになり、それができるならそもそも仕分けは要らない。

**T0 は T1 の代理**として使う。代理が使えるかどうかは仮定ではなく実測できるので、
§5 で必ず確かめる。

### 1.2 手で作るのは「場所ラベル」であって「窓」ではない

仕分けの出力は**窓（重なりつきの被覆）**だが、**窓を手で作ってはいけない。**

- 窓は容量 `C` と重なり率 `r` から機械的に決まる（設計 §3.3）。人が作る余地が無い
- 人が作った窓は再現できない。**同じ人がもう一度作っても違う窓になる**
- 窓の良し悪しは、ラベルさえあれば計算できる（§4.5）

人にしか言えないのは **「どの写真とどの写真が同じ場所を写しているか」** の 1 点で、
そこだけを作る。

### 1.3 ラベルの定義（ここが曖昧だと全部が曖昧になる）

> **ラベル = 中で数珠つなぎに「同じ面」を共有している写真の集まり。**

3 つの但し書きが要る。

1. **全部が全部と重なっている必要は無い。** 部屋の東の壁と西の壁は互いに写って
   いなくてよい。間の写真が繋いでいればひと続きである（再構成が要求するのも
   これで、全ペアの重なりではない）
2. **建築的な「部屋」とは違う。** 廊下から続けて撮った吹き抜けは、壁が繋がって
   いれば同じラベルでよい。逆に、同じ部屋でも間を撮っていなければ 2 つに分ける
3. **戻ってきた撮影は元のラベルへ戻す。** これが時刻からは絶対に作れない情報で、
   **正解のいちばんの価値がここにある**（#11 が解こうとして解けなかったもの）

### 1.4 正解には「分からない」という状態を持たせる

判断できなかった写真は `_不明/` へ入れる。**「たぶん A」を A に入れてはいけない。**
1 枚が指標の成績を静かに嵩上げし、しかもどれを嵩上げしたか後から分からなくなる。

同じ理由で、使えない写真（真っ暗・大きくブレた・関係の無い被写体）は `_除外/` へ
入れる。これは仕分けの正解ではなく、**品質フィルタの正解**として別に効く。

## 2. 人の手順

### 2.1 フォルダ規約

```
truth/
  001-玄関/            場所ラベル 1 つ。先頭の数字は**現地を歩く順**
  002-廊下/            （隣接の判定に使う。数字が無ければ名前順）
  003-リビング/
  _除外/               使わない写真
  _不明/               判断できなかった写真
  _sheets/             接触シート（道具が作る。人は触らない）
```

- **1 枚を 2 つのラベルへ入れてよい**（戸口の写真など）。仕分けの正解は分割では
  なく被覆なので、「どちらにも属する」は正しい状態である
- ラベルの中でフォルダを掘ってもよい（中身は同じラベル扱い）
- 名前は自由に変えてよい。**写真の同一性は inode で見ている**ので、名前を変えても
  フォルダを掘っても元の写真へ正しく戻る

### 2.2 手順

**1. 下書きを作る**（数分）

```bash
swiftc -O scripts/measure-truth.swift -o /tmp/measure-truth
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --draft 50
```

撮影順に 50 枚ずつのフォルダができる。写真は**ハードリンク**なので、原本は
1 バイトも動かず、ディスクも増えず、Finder で自由に動かせる。ファイル名の頭に
撮影順の番号が付くので、**Finder の名前順がそのまま撮影順**になる。

**2. Finder でフォルダを直す**（1424 枚で 1〜2 時間）

写真を 1 枚ずつ見る作業ではない。実際にやることは 3 つしかない。

| やること | 頻度 |
| --- | --- |
| **境界をずらす**（前後のフォルダへ数枚移す） | フォルダの数だけ |
| **フォルダを結合する**（1 つの場所が 2 つに割れている） | しばしば |
| **戻ってきた区間を元のラベルへ移す** | 現場による。**ここがいちばん価値がある** |

フォルダに名前を付ける（`001` → `001-玄関`）のは最後でよい。

**3. 見直す**（20 分）

```bash
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --sheets \
    --cache ~/Desktop/trial/cache.bin
open ~/Desktop/truth/_sheets/index.html
```

**`--cache` は毎回付ける。** サムネイルと視覚特徴が残っていれば写真を 1 枚も
デコードし直さないので、2 回目からの `--sheets` は一瞬で終わる（付けないと
1424 枚のデコードで数分かかり、見直しの往復が続かない）。

3 つのページができる。それぞれ違う間違いを見つけるためのもの。

| ページ | 見つかるもの |
| --- | --- |
| `index.html` | 分けすぎ・混ぜすぎ（枚数と**撮影順の塊の数**が並ぶ） |
| `folder-*.html` | 迷い込み（**赤枠が撮影順の飛び**＝再訪かもしれない） |
| `sequence.html` | **境界と再訪**（全部を撮影順に並べ、ラベルが変わるところで区切る） |

**4. 道具に候補を出させる**（任意・10 分）

```bash
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --hints
```

「別のラベルのほうがはっきり近い写真」「1 つにまとめる候補のラベル対」「塊が
4 つ以上のラベル」が出る。**採否は必ず写真を開いて決める**（理由は §3.2）。

**5. 読み戻して採点する**（数分）

```bash
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --analyze \
    --cache ~/Desktop/trial/cache.bin
```

### 2.3 迷ったときの原則

1. **同じ面が写っているかで決める。** 「同じ部屋か」ではない
2. **間を撮っていなければ分ける。** 数珠つなぎが切れているところが境界
3. **迷ったら `_不明/`。** 混ぜるより空けるほうが安い（§1.4）
4. **枚数の多すぎるラベルを、枚数を理由に割らない。** 容量は道具側の仕事で、
   正解の側に持ち込むと「正解が窓に似てくる」（§3.1 と同じ汚染）

## 3. 正解を汚さないための手当て

### 3.1 下書きの種は撮影順にする（**自動の窓から始めない**）

`--draft` は撮影順の等分しか作らない。`measure-ordering --windows` の出力から
始められるようにはしていない。**採点される側の答えを写して正解を作ると、
その手法だけが良い点を取る**からである。

撮影順は「人が実際に歩いた順」なので、いちばん近く、いちばん偏りの少ない
出発点になる。ただし**これも偏りではある** — 撮影順で切った境界がそのまま残る。
`sequence.html` で境界を見直すのは、この偏りを剥がす作業でもある。

### 3.2 `--hints` は「見る場所」を絞るためだけに使う

候補は視覚特徴（feature print）が計算している。それをそのまま正解へ反映すると、
**視覚特徴を視覚特徴で採点する**ことになり、§4.1 の成績が意味を失う。

したがって `--hints` は 2 つの制約付きで使う。

- **最初の 1 周では使わない。** 一通り自分で作ってから、抜けを探すのに使う
- **候補は必ず写真を開いて決める。** 「近いと言われたから移す」をしない

道具の側でも、はっきり近いとき（現在のラベルの 0.8 倍未満）しか候補を出さない。

### 3.3 番号は歩く順に付ける

`001` `002` … は**現地の隣接**を表す。隣り合う番号のラベル同士は「歩く順で
隣」として扱われ、**指標がいちばん間違えやすい相手**として別に採点される
（§4.1 の「隣接 AUC」）。番号が適当だとこの列が意味を失う。

## 4. 何が測れるようになるか

`--analyze` の出力と、それが答える未解決を並べる。

### 4.1 指標の分離能 — **どの指標を信じるか**

```
指標                組(同)   組(別)   AUC  隣接AUC  同中央  同90%  別中央  90%時誤り  最良J  その閾値
視覚特徴の距離      120480  893211  0.94    0.71    0.21   0.38    0.55      0.12     0.71    0.33
撮影順の隔たり      120480  893211  0.88    0.55     34     312     640      0.31     0.62     180
…
```

- **AUC** … 同じ場所の組のほうが小さい値になる確率。0.5 は当てずっぽう。
  閾値を選ばずに指標そのものを比べられるので、ここが指標比較の軸になる
- **隣接 AUC** … 相手を「歩く順で隣のラベル」に限ったもの。**実際に間違えるのは
  ここ**で、全体が 0.94 でも隣接が 0.6 なら現場では使えない
- **90%時誤り** … 同じ場所の 9 割を拾う閾値を置いたとき、違う場所を拾う割合。
  **#11 の「閾値方式」が成立するかは実質この 1 つの数字で決まる**

答える未解決: #11 の閾値の自動決定、#12 のインライア率、そして
「時刻・GPS・露出・知覚ハッシュのどれをまだ使う価値があるか」。

### 4.2 近傍の質 — **順位だけ使う**という設計の実測

設計 §2.1 は「距離の絶対値ではなく順位だけを使う」としている。順位で使ったときの
成績（上位 k 件の同ラベル率と取りこぼさない率）を、無作為の水準と並べて出す。
§6.1 の「上位 30 の再現率 0.88」は**撮影順で隣り合う写真**を正解の代わりにした
数字だったので、**戻ってきた撮影を含む本当の正解で測り直す**ことになる。

### 4.3 共視グラフの辺 — **共通近傍フィルタは実データで効くのか**

設計 §2.2 のフィルタは、**合成グラフでしか確かめていない**（「孤立した空似を
100% 除き、真の辺を 1 本も失わない」）。正解があれば実データで

```
フィルタ前  辺 8214 本（採点できた 7980 本）  同じ場所 0.83
共通近傍後  辺 6102 本（採点できた 5930 本）  同じ場所 0.91
→ 空似を 1180 本落として、本物を 870 本失った
```

のように、**何を落として何を失ったか**が出る。

### 4.4 空似の地図 — **§9-2 を名指しにする**

違う場所どうしが辺で結ばれた回数を、ラベル対で数える。上位に並ぶのが
**この現場で実際に空似を起こしている組**で、「歩く順で隣」でない組が上位に
来たら、それが設計 §9-2 の「かたまりの空似」である。

**どのラベルとどのラベルが取り違えられているかが分かれば、対策を打つ場所が
決まる**（例: 白い壁の部屋どうしだけなら、そこに撮影の指摘を出すという手も
ありうる）。

### 4.5 窓の採点 — **自動の結果を、いつでも数分で採点できる**

```bash
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth \
    --score ~/Desktop/trial/rounds/003/windows
```

被覆に分割の指標（ARI など）は使えないので、設計が実際に必要としている 2 つを見る。

| | 意味 | 設計での重み |
| --- | --- | --- |
| **ラベル被覆率** | そのラベルの写真が、どれか 1 つの窓へどれだけ入ったか | **こちらが主**。低い＝分断 |
| 窓の純度 | 窓の中で最大のラベルが占める割合 | 説明用。低い＝混入（安い） |

§1.2 のとおり「混入は安い・分断は高い」ので、**見るのはまず被覆率**である。
純度が低いこと自体は問題ではない（Object Capture が使えない写真を捨てる）。

**そして `ledger.tsv` の成否と窓の名前で突き合わせられる。** §6.2.9 は
「内部指標は成否を予言しない」ことを示したが、**正解由来の指標（純度・被覆率）
なら予言するのか**は、これで初めて測れる。予言するなら、窓を投げる前に良し悪しを
判定できることになる。

### 4.6 撮影順は場所の証拠か — **§10 の A/B/C を数字で決める**

設計メモ §10 は「撮影順を証拠として使うか」を A（使わない）/ B（順位付けだけ）/
C（窓を作るのに使う）の 3 択で残した。決め手になる数字が 3 つ出る。

- 撮影順で隣り合う 2 枚が同じ場所である割合
- 同じ場所の組の撮影順の隔たり（中央値・90% 点）
- 2 つ以上の塊に分かれるラベルの数（＝戻ってきた撮影の実態）

隣り合う割合が高く、隔たりの 90% 点が小さければ **C** が成立する。塊に分かれる
ラベルが多ければ、撮影順だけでは足りない（＝ #11 が解こうとしていた問題が
この現場に本当にある）。

## 5. 正解そのものを検算する（これを最初にやる）

**T0（人の目）が T1（幾何）の代理になるかは、仮定してはいけない。**

`--read` は `truth-windows/` に、ラベルごとの写真一覧を
`measure-poses.swift --window-dir` がそのまま食える形で書き出す。

```bash
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --read --capacity 200
/tmp/measure-poses ~/Pictures/現場 --window-dir ~/Desktop/truth-analysis/truth-windows \
    --poses-out ~/Desktop/truth-analysis/poses --timeout 3600
```

結果は 3 通りで、**どれが出るかで設計の次の一手が変わる**。

| 結果 | 意味 | 次の一手 |
| --- | --- | --- |
| だいたい通る | 人の「同じ場所」＝再構成できる単位。**正解として使える** | §4 の採点へ進む |
| **屋内だけ落ちる** | §9-11 の答え。窓の作り方の問題ではなく**撮影そのもの**の問題 | 窓の作り方をいくら直しても通らない。撮り直しの指摘が製品の仕事になる |
| ばらばらに落ちる | ラベルの粒度が大きすぎる（数珠つなぎが切れている） | ラベルを割ってから再挑戦 |

2 行目が出た場合が重要で、**#13 / #14 の設計の合否とは無関係に、この現場では
屋内が通らない**ことになる。§10 の「次に走らせる 3 つ」の 1 番目（屋内 100 枚を
撮影順で投げる）と同じ問いに、**人が選んだ最良の入力で**答えることになる。

## 6. コマンドまとめ

```bash
swiftc -O scripts/measure-truth.swift -o /tmp/measure-truth

# 下書き（撮影順 50 枚ずつ・ハードリンク・接触シートつき）
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --draft 50

# …Finder で直す…

# 接触シートを作り直して見直す（--cache があれば読み直しゼロ）
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --sheets \
    --cache ~/Desktop/trial/cache.bin

# 読み戻し（truth.tsv と truth-windows/）
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --read --capacity 200

# 採点（指標の分離能・近傍の質・空似の地図・撮影順の検証）
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --analyze \
    --cache ~/Desktop/trial/cache.bin

# 自動の窓を採点
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth \
    --score ~/Desktop/trial/rounds/003/windows

# 見直しの候補（**最初の 1 周では使わない**）
/tmp/measure-truth ~/Pictures/現場 --truth ~/Desktop/truth --hints
```

`--cache` は `measure-ordering.swift` と**同じファイルを共用する**（形式も同じ）。
`trial-clustering.sh` を回したあとなら、視覚特徴の読み直しは起きない。

### 出力の扱い

| | 中身 | 共有 |
| --- | --- | --- |
| `metrics.tsv` / `confusion.tsv` / `score-*.tsv` / 画面の表 | 数値とラベル名だけ | **そのまま共有してよい**（`--anonymous` でラベル名も伏せられる） |
| `truth.tsv` / `hints.tsv` / `_sheets/` | ファイル名・写真 | **手元専用** |

### 道具そのものの確認

```bash
./scripts/truth-selftest.sh          # macOS が要る。GPU は要らない
```

合成写真（2 部屋 48 枚）で下書きから採点まで通し、**正しい正解とでたらめな正解で
成績が期待どおり変わること**まで確かめる。`trial-clustering.sh` が実データを通す
過程で踏んだ 4 つの誤り（§10 の申し送り）はすべて「道具が黙って嘘をつく」形
だったので、人が 1〜2 時間かける前にここを通す。

## 7. この方法が間違っているとしたら、どこか

1. **人の目が共視の代わりになる保証は無い。** 白い壁を「同じ壁」と見分けられて
   いないかもしれず、逆に人には別の部屋に見えても幾何的には繋がるかもしれない。
   **§5 の検算がこれを直接見る**ので、正解を作ったら真っ先にやる
2. **1 人が 1 回作った正解には系統的な癖がある。** とくに境界の置き方。理想は
   2 人（または日を置いて 2 回）作って食い違いを見ることだが高い。せめて
   **迷った写真は `_不明/` へ**入れておけば、癖が指標の成績へ流れ込まない
3. **正解は 1 つの現場のもの**である。ここで選んだ指標が別の現場で成り立つ保証は
   無く、とくに複数人・複数日の撮影は §9-6 のまま未検証である。**指標を正解へ
   合わせ込みすぎない**（AUC が 0.02 高いほうを選ぶ、といった使い方をしない）
4. **正解が「窓に似てくる」危険。** 枚数を理由にラベルを割ったり、自動の窓を見て
   から直したりすると、採点は自分自身を採点することになる。§2.3-4 と §3.1 が
   この 1 点への手当てである
5. **ラベルの粒度を人が決めている。** 「数珠つなぎで繋がっているか」は連続量で、
   どこで切るかに幅がある。§5 でばらばらに落ちるなら粒度が粗すぎ、逆に全部が
   小さすぎれば隣接 AUC が測れなくなる（隣り合うラベルばかりになる）
